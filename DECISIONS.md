# DECISIONS

Design decisions that had real alternatives, and why this one won.

Log a decision when a reasonable engineer could have chosen differently. Skip anything with only one sensible option.

Format:

```
### <decision>
**Context:** what forced a choice
**Options:** what was considered
**Chose:** the option taken
**Because:** the reasoning
**Cost:** what this gives up
```

---

### Money stored as integer paise
**Context:** Every amount in the system needs a representation.
**Options:** Float rupees; decimal type; integer paise.
**Chose:** Integer paise.
**Because:** Floats lose precision on arithmetic, and spend caps depend on exact comparisons — a cap breach that rounds the wrong way is a graded failure. Razorpay's own API uses paise, so no conversion at the boundary.
**Cost:** Must convert at every display point.

### Groq as default LLM, Gemini reserved
**Context:** Two free-tier providers available, both rate-limited.
**Options:** Gemini default; Groq default; route per task type.
**Chose:** Groq default, Gemini only for tasks that visibly fail on Groq, always with Groq fallback.
**Because:** Gemini's free tier rate-limits fast enough to break a live demo. Demo reliability outweighs per-call quality for classification and conversation, which is most calls.
**Cost:** Some reasoning-heavy tasks may need prompt work to hold quality on Groq.

### The gate is a module every money action calls, not middleware
**Context:** Spend caps must apply to money actions from three different surfaces.
**Options:** HTTP middleware on payment routes; a gate module every action calls explicitly; DB-level constraints.
**Chose:** An explicit module call.
**Because:** Middleware only covers HTTP paths — it would miss webhook-triggered recovery actions and internal reward issuance, which are money actions too. An explicit call is greppable, so coverage is auditable. DB constraints can't express reason or produce an explanation.
**Cost:** A new money action can forget to call it. Mitigated by making the gate the only module that touches the Razorpay payment client.

### AI decides judgment, deterministic code decides limits
**Context:** Where the LLM is allowed to influence money.
**Options:** Let the model reason about caps holistically; hard split.
**Chose:** Hard split — models never compute or evaluate a bound.
**Because:** Both track bars require bounds be provable. A model cannot guarantee arithmetic, and "the LLM decided it was within budget" is not defensible to a judge. The split is itself a graded criterion.
**Cost:** Less flexible than a model weighing tradeoffs holistically.

### Layer 3's failed payments are simulated; the recovery path is real
**Context:** Recovery needs a supply of failed payments, but nothing in this codebase can pay a Razorpay order server-side — there's no checkout until Layer 4, so there's no organic way to produce a genuine decline.
**Options:** Fabricate the whole thing (insert rows describing payments that never happened, flip a status column to "recovered"); block Layer 3 entirely until Layer 4's checkout exists; simulate only the failure and drive everything downstream of it for real.
**Chose:** Simulate the failure, keep the recovery entirely real. A `payment_failures` row carries a real decline code; everything downstream — diagnosis (a real model call), policy (real deterministic arithmetic), the sequencer (real `attemptMoneyAction()` calls creating real Razorpay orders against the merchant's own account) — runs unmodified. `source: "webhook" | "simulated"` is a display-only column the pipeline logic must never branch on, so the same code path handles a real webhook delivery the day one arrives.
**Because:** Blocking the highest-scoring layer on a lower-priority one would have ended the buildathon with three half-built layers instead of a complete submission. Fabricating outcomes would have made the audit trail and the recovered-rupees figure decorative rather than real, which fails CLAUDE.md's core bar directly.
**Cost:** `recoveredPaise` was honestly always 0 in Layer 3, since no order created there could ever be verified as paid without a real checkout — the demo proved restraint and gate composition, not a positive recovered-money figure. **Resolved in Layer 4-3:** `retry_same_instrument`/`alternate_instrument` now create a real, payable Razorpay Payment Link through the gate; `recoveredPaise` is set only from the `payment_link.paid` webhook's verified amount (`recovery/sequencer.ts`'s `confirmRecoveryLinkPaid`), never optimistically. Generating the link is real; delivering it to the customer by email/SMS is still not wired (no messaging provider) — that half remains explicitly unreal, stated on the attempt's own `reason` text rather than left unlabelled.

### Recovery attempts are bounded by the same spend cap as any other agent
**Context:** A recovery attempt that moves money needs an `agents.id` to answer to — `attemptMoneyAction`'s bound checks are keyed on agent status and spend cap, and the recovery pipeline isn't any particular external buyer agent.
**Options:** Give the recovery pipeline a bypass around the gate's cap checks (it's "the merchant," not an untrusted agent); create a separate, uncapped recovery budget; provision a real, capped `agents` row for the recovery pipeline like any other agent.
**Chose:** A lazily-provisioned, hidden `__recovery_pipeline` agent per merchant, with its own real spend cap, going through the exact same `attemptMoneyAction()` gate as any external buyer agent.
**Because:** A bypass would mean the single most differentiated Track 01 moment in the product — "the recovery agent is bounded by the same rules as everything else" — wouldn't actually be true. It also means a cap-exhausted recovery attempt is a normal, already-tested code path (a gate denial) rather than a new failure mode to handle separately.
**Cost:** An extra internal agent row per merchant that never appears in the dashboard's agent list, and a generous default cap that exists mainly so the gate doesn't block recovery before `policy.ts`'s own ROI governor gets a chance to.

### `recoveredPaise` lives on the attempt, not the failure
**Context:** Attribution needs to sum "how much came back," and a single failed payment can have multiple recovery attempts.
**Options:** A single `recovered_paise` column on `payment_failures`; a `recovered_paise` column on each `recovery_attempts` row, summed for attribution.
**Chose:** On the attempt.
**Because:** Attribution needs to point at *which* attempt recovered the money, not just that some amount eventually did — and keeping it non-zero only on an outcome of `"succeeded"` (enforced by the sequencer, checked by a dedicated test) makes double-counting structurally harder: there's no code path that both writes a non-zero amount and marks an attempt anything other than succeeded.
**Cost:** Attribution requires a join/aggregation across `recovery_attempts` rather than a flat read of `payment_failures` — a small query cost for a stronger invariant.

### No mocks in the test suite
**Context:** Tests for the gate and the LLM wrapper need to exercise failure paths (a Razorpay rejection, a Gemini outage) without waiting on unreliable real-world conditions.
**Options:** Mock the SDK boundary to force failures deterministically; provoke genuine failures instead (an amount below Razorpay's minimum, an invalid Gemini model name).
**Chose:** Genuine failures only. A stress test already caught a real bug (a dynamic import that silently failed to resolve) that a mocked suite could never have seen, since the mock intercepted the call before module resolution mattered.
**Cost:** Slower test runs, real API calls on every run, and the Gemini-fallback proof lives in a standalone script rather than inside the vitest suite, since forcing a real Gemini failure needs a broken client construction that doesn't fit `complete()`'s public input shape.

### Checkout mechanism: Razorpay Checkout (hosted JS), never server-side card capture
**Context:** L4-2 needed a real way for a human buyer to pay. Razorpay offers both a hosted/embedded JS checkout (Checkout.js) and a server-to-server card API.
**Options:** Server-side S2S card payments (`payments.createPaymentJson`), taking card details directly; Razorpay Checkout, the hosted widget that never lets card data touch this server.
**Chose:** Checkout.js. The server only ever creates an order and later verifies a signature; the browser talks to Razorpay directly for the card/UPI/OTP flow.
**Because:** S2S card payments bring PCI DSS scope and OTP/3DS handling this project has no business taking on for a buildathon submission, and CLAUDE.md's own architecture note (in `razorpay.ts`'s original docstring) already anticipated this. A client-reported success is never trusted on its own either way — `/api/checkout/verify`'s HMAC check against the merchant's own key secret is the actual proof, with the `payment.captured`/`order.paid` webhook as the backstop if the browser call never lands.
**Cost:** Requires loading Razorpay's external `checkout.js` script client-side and a slightly more involved flow (create order → open widget → verify signature) than a single server call would be.

### Escrow holds modelled as a `money_actions.status = "held"` plus a dedicated `escrow_holds` table
**Context:** L4-5 needed a hold-and-capture state distinct from a normal auto-captured purchase, explicitly visible/resolvable from the dashboard (not just inferred from Razorpay's own state), with a deterministic expiry.
**Options:** A separate `escrow_holds` table carrying its own full status lifecycle, decoupled from `money_actions`; add `"held"` as a `money_actions.status` value and a lean `escrow_holds` table that only carries the expiry/outcome bookkeeping `money_actions` doesn't need.
**Chose:** The second — `"held"` sits in the same status enum every other money action lifecycle uses (`executed` → `held`/`captured`, `held` → `captured`/`refunded`), and `escrow_holds` exists only for `expiresAt`/`outcome`/`resolvedAt`, referencing `money_actions` by id rather than duplicating its fields.
**Because:** One status lifecycle is easier to reason about than two, and every existing gate function (`confirmCapture`, `releaseBudget`, the audit trail) already understood `money_actions.status` transitions — extending that enum reused all of it. A fully separate table would have meant a second parallel state machine gate.ts's capture/refund functions would both need to know about.
**Cost:** `money_actions.holdOnly` (a boolean, set at order-creation time) is needed to tell `confirmCapture` which target status (`held` vs `captured`) a verified payment should land in — one extra column threaded through the request/execute path, versus the alternative's cleaner separation.

### Recovery Payment Links create their own Razorpay entity, not built on an order — the gate only bounds the spend, doesn't own the artifact
**Context:** L4-3's `retry_same_instrument`/`alternate_instrument` strategies needed to produce something a customer could actually pay later, asynchronously. Razorpay Payment Links are a separate entity from Orders — a link isn't created against an existing order id.
**Options:** Keep `attemptMoneyAction` creating a real order (as before) purely for the audit trail/spend-cap bound, and have the sequencer separately create a standalone Payment Link tracked only on `recovery_attempts`, disconnected from the gate; extend the gate itself so `MoneyActionRequest.paymentLink` makes `executeAndSettle` create a Payment Link instead of an order, still reserving budget through the exact same bound checks.
**Chose:** The second. `money_actions.razorpay_entity_id` stores the Payment Link id instead of an order id when `paymentLink` is set; everything else (budget reservation, stock, the audit trail, idempotency) is unchanged.
**Because:** Two Razorpay entities per recovery attempt (an order nobody pays, plus a link that's the real artifact) would have been exactly the kind of decorative money action CLAUDE.md rules out, and would have meant the audit trail's "what actually happened" no longer matches "what the customer can pay." One code path, one artifact, same bound checks.
**Cost:** `GateResult` now carries an optional `paymentLinkUrl`/`paymentLinkId` alongside the existing `razorpayOrderId`, and `executeAndSettle` branches on which kind of Razorpay entity to create — a small increase in that function's surface area for a real capability (Layer 4-2's checkout still only ever uses the order path).

### Buyer chat conversation state: dedicated `conversations`/`messages` tables, not client-only
**Context:** L4-6 needed somewhere for chat history and the code-computed cart to live across turns.
**Options:** Client-side/in-memory state only (React state, lost on reload); dedicated DB tables keyed by a browser-generated session token, no buyer login required.
**Chose:** `conversations` (merchantId, sessionToken, cartProductId, cartQuantity) and `chatMessages` (role, content), following this codebase's existing convention of DB-backing everything (sessions, escalations, spend caps) rather than trusting client state for anything that matters.
**Because:** The cart's productId/quantity are exactly the kind of state CLAUDE.md rule 2 says code must own deterministically — putting them only in browser memory would make "the LLM proposes, code decides and persists" much harder to audit, and a page reload losing the cart mid-conversation is a bad buyer experience for no real savings in complexity.
**Cost:** Two new tables and their migration, and every chat turn does a few extra DB round-trips (insert message, load/update cart, insert reply) compared to a stateless client-only design.

### Product variants as a child table, not attributes-on-row
**Context:** L5-1 needed to model real catalogues — a coffee bag in 250g/1kg, a mug in three colours — where the current one-row-one-price-one-stock `products` table can't express a sellable unit smaller than "the whole product."
**Options:** Option A — `products` becomes the marketing-level entity (title, description, category, policy-adjacent fields); a new `product_variants` table holds `sku`, `pricePaise`, `costPaise`, `stock`, `attributes`, `availability`, `gtin`/`mpn`, `imageUrl`, and the gate's `productId` becomes `variantId`. Option B — keep one row per sellable thing, add an `attributes jsonb` column and a `sku`, relate two sizes by a shared `groupId`.
**Chose:** Option A.
**Because:** A variant is a first-class thing an agent selects by a stable id, not a string it fuzzy-matches — that's the entire point of this layer (an agent choosing correctly, not guessing). It's also the shape every real catalogue system converges on, and it gives Layer 6's margin-aware upsell a clean per-variant `costPaise` seam instead of a `jsonb` blob nothing can validate. Option B avoids migrating the money path, but that's a one-time cost; the jsonb-blob cost would be paid on every future feature that reads structure back out of it.
**Cost:** The money-path migration is real: `money_actions` gains `variant_id` alongside the existing `product_id` (never repurposed — past rows keep pointing at a valid product), `gate.ts`'s `resolveProduct`/`reserveStock`/`releaseStock` move to operate on `product_variants`, and every existing seeded product needs a default variant created as part of the migration so nothing orphans. `gate.products.test.ts`'s concurrency test is re-pointed at the new table with only ids changed — if it stops passing, the gate contract broke.

### MCP auth reuses the existing agent API key as a bearer token, not OAuth 2.1
**Context:** L5-4's MCP server needs to authenticate a calling agent. The MCP spec's documented answer for remote servers is OAuth 2.1 with the server as a Resource Server advertising `.well-known` metadata.
**Options:** Implement OAuth 2.1 Resource Server metadata + a delegated consent flow; reuse `agent-auth.ts`'s existing `Authorization: Bearer <raw-key>` scheme, the same one `/api/agent/*` already authenticates with.
**Chose:** Reuse the existing bearer-key scheme.
**Because:** It's real authentication that already inherits every isolation guarantee `isolation.test.ts` proves, an agent with a key can use the REST API and MCP interchangeably, and it avoids standing up a second identity system for a buildathon submission. Same reasoning that put merchant-pasted Razorpay keys ahead of Razorpay OAuth in Layer 2.
**Cost:** Not spec-compliant OAuth 2.1 — no delegated user consent flow, no token scoping finer than "this agent's own spend cap." Documented here and in ARCHITECTURE.md as the honest state; OAuth 2.1 is the upgrade path if this ever needs third-party agent platforms to self-provision access rather than a merchant handing out a key directly.

### This product exposes its own MCP server, not Razorpay's
**Context:** prd.md names "Razorpay MCP server" as the tool layer, and Layer 0's build-order row claimed it was wired — neither was true (`grep -ri mcp src/` returned nothing going into L5).
**Options:** Wire up Razorpay's own MCP server; build and expose this product's own MCP server.
**Chose:** This product's own server.
**Because:** Razorpay's MCP server exposes a merchant's own Razorpay account operations (create order, fetch settlements, issue refunds) as tools for the merchant's assistant — the opposite direction from what §1 needs, which is an external buyer's agent discovering and transacting with a merchant it has never integrated with. Razorpay's server does nothing to make a merchant agent-discoverable.
**Cost:** A new dependency (`@modelcontextprotocol/sdk`) and protocol surface to build and maintain, versus wiring up something that already exists — justified because the two solve genuinely different problems, not because the existing option was hard to configure.

### Catalogue import: preview-then-confirm, never model output straight to the database
**Context:** L5-2's paste-a-blob import path asks an LLM to extract structured product rows from unstructured text (a supplier email, a pasted list). A hallucinated price or quantity would be a real mispriced product the gate would happily let an agent buy at.
**Options:** Write extracted rows directly to `products`/`product_variants`; require merchant confirmation of a preview before any write.
**Chose:** Preview then confirm — extraction never writes, only a merchant pressing "Import" writes.
**Because:** Same principle already established in `chat.ts`'s `applyIntent` (the model proposes, code validates and writes) — except here the failure mode is worse, since chat's cart is corrected by the next message and a live catalogue price is what a buyer agent actually pays. CSV rows are parsed deterministically in code (never sent to an LLM) for the same reason: a model silently dropping a row is a data-integrity bug invisible until someone notices missing stock.
**Cost:** An extra confirmation step in the merchant's import flow, and a `catalogue_imports` table to track what was parsed/imported/skipped per run — more surface than "upload and done," in exchange for never letting unconfirmed model output become a live, purchasable price.

### Merchant terms are structured fields, not prose a model parses at read time
**Context:** L5-3 needed return/refund/shipping terms an agent can act on ("is this returnable, in what window") — prd.md §1 idea #4.
**Options:** A free-text policy blob a model interprets when an agent asks; dedicated structured columns (`returnsAccepted` boolean, `returnWindowDays` integer, `refundMethod` enum, etc.) with a generated human-readable sentence derived from them for display.
**Chose:** Structured columns, generated prose for display only.
**Because:** Putting a model between a buyer agent and a contractual term makes every read non-deterministic — the same "AI decides judgment, code decides limits" split CLAUDE.md states for money applies here too, since a return window is effectively a bound an agent reasons about. A merchant with no policy set reads as "not published," never a fabricated permissive default (e.g. inventing "30-day returns") that could misrepresent what the merchant actually offers.
**Cost:** A merchant fills out structured fields instead of writing one paragraph; the fixer/scorer (L5-6) has to prompt for the specific missing field rather than accepting any free text as "done."

### The public discovery manifest includes real prices, and makes no standards-conformance claim
**Context:** L5-5's `/store/[merchantId]/manifest.json` needs to be useful to an agent that hasn't authenticated yet — but real prices are also information a merchant might not want republished at a second, unauthenticated URL.
**Options:** Omit prices from the manifest, showing only a catalogue summary (counts/categories) and requiring a key to see anything transactable; include a real price range and let it stand, since the same prices are already public on the storefront page itself.
**Chose:** Include prices (`catalogueSummary.priceRangePaise`), reasoning explicitly that this is not a new disclosure — the storefront (`/store/[merchantId]`) already shows every price to anyone with the URL, unauthenticated. Also chose not to claim conformance to any external discovery standard (ACP, AP2, x402, NPCI's UAP) — the manifest is a clean, self-describing JSON document plus a real MCP server, not an implementation of a spec this project doesn't actually follow.
**Because:** Withholding a price that's one click away on the same merchant's own storefront would be security theater, not a real privacy boundary — and prd.md explicitly names those external standards as things to reference correctly in the pitch, not integrate; claiming conformance without having implemented it is the kind of thing that collapses under one question from a judge.
**Cost:** A merchant who wants their prices genuinely unauthenticated-unreachable would need to gate the storefront itself, not just the manifest — out of scope for this layer.

### Basic in-memory rate limiting, reconsidered for L4's new public endpoints
**Context:** Layer 2 deferred rate limiting to "a real deployment." L4 adds genuinely public, unauthenticated endpoints that hit the LLM (`/api/chat`) or create real Razorpay orders (`/api/checkout/*`) on every call — a more pressing abuse surface than the dashboard/agent routes the original deferral was about.
**Options:** Keep deferring everything, document the gap explicitly; add a real (Redis-backed or similar) distributed limiter; add a minimal in-memory per-key sliding-window limiter.
**Chose:** The minimal in-memory limiter (`src/lib/rate-limit.ts`), applied to `/api/chat`, `/api/checkout/order`, `/api/checkout/verify`, `/api/agent/purchase`, and the login Server Action.
**Because:** A real distributed limiter is infrastructure this single-instance buildathon deployment doesn't have and doesn't need yet; an in-memory limiter is a genuine, working guard against the obvious abuse case (a script hammering one endpoint from one IP) rather than nothing, which is the honest bar for what this layer needs — not a claim of production-grade, multi-instance abuse protection.
**Cost:** Resets on process restart and doesn't share state across multiple instances — explicitly not a substitute for a real distributed limiter if this is ever deployed behind more than one server process.

### How a discount is represented, without weakening the gate's price-match bound
**Context:** Layer 6 (upsell/bundling) needs a buyer to pay less than the catalogue price when a bundle offer is accepted. The gate's `product_price_match` bound (Layer 4-1/5-1) denies any request whose `amountPaise` doesn't equal `variant.pricePaise * quantity` exactly — the single most important bound in the codebase, since it's what makes "the caller cannot name its own price" true.
**Options:** Let the caller assert a discounted `amountPaise` directly, with the gate trusting a `discountReason` or similar as justification; charge full catalogue price and issue the discount as a separate refund/credit after; a merchant-authored discount (a `bundles` row with an integer-paise `bundlePricePaise`) that a caller can only *reference* by an `offerId`, with the gate independently re-deriving the expected amount from that row and denying on any mismatch — identical in spirit to `product_price_match`, just resolved against a bundle instead of a variant.
**Chose:** The third — an `offerId` on `MoneyActionRequest`, resolved by a new `discount.ts` module (`resolveOffer`) that checks the offer belongs to this merchant, was actually accepted (not just offered, declined, or expired), hasn't passed its deterministic `expiresAt`, and was made to the identity now redeeming it (agent or session token) — then hands the gate the bundle's own `bundlePricePaise`, which `checkBounds` compares against the caller's asserted `amountPaise` with the same "deny on any mismatch" discipline `resolveVariant` already uses.
**Because:** The caller still cannot influence what it pays by anything in the request body — it can only point at something the merchant already authored, and the gate re-derives the number itself every time, from a row a merchant wrote through `bundles.ts`'s `createBundle()` (which itself enforces a maximum discount percent and a cost floor before the row can even exist). This keeps `product_price_match`'s guarantee completely intact — a purchase that asserts its own discounted amount with no valid offer referenced is still denied, proven by `gate.offers.test.ts`'s first test. The full-price-then-refund option would have meant a worse buyer experience (charged full price, credited later) for no real safety gain, since the refund path is exactly as trustable as the discount path either way.
**Cost:** A bundle purchase covers multiple variants, not one, so the gate's stock reservation had to grow from a single atomic conditional-`UPDATE` to an all-or-nothing loop over every bundle item (`reserveOfferStock`/`releaseOfferStock` in gate.ts) — each item still uses the same atomic `WHERE stock >= quantity` pattern individually, but a losing item now rolls back every item already reserved in that same call, which is more surface area than the single-variant path. `money_actions` also gained a new nullable `offerId` column (never repurposing `productId`/`variantId`, same discipline as Layer 5-1's `variantId` addition).

### L6-6 (abandonment-to-upsell recovery strategy) cut, not built
**Context:** The Layer 6 plan's L6-6 asked for a new recovery strategy — when a failure's cause is the product (out of stock) rather than the payment instrument, offer an available alternative instead of retrying the identical purchase. Investigating it against the real schema before writing code: `payment_failures` (Layer 3) has no product or variant reference at all — `declineCode`/`declineDescription` are the only signal, and the whole pipeline was built to reason about payment instruments, never about what was being bought.
**Options:** Force a shallow version in anyway (e.g. branch on a decline-description substring that vaguely suggests stock, without any real product link); do the schema work properly — add a nullable `variantId` to `payment_failures`, thread it through `intake.ts`'s writer, `diagnose.ts`, and a new `policy.ts` branch with its own stopping rules; skip it this pass, following the plan's own explicit guidance ("if the layer is running long, cut this before cutting L6-4").
**Chose:** Skip it, documented here rather than silently dropped.
**Because:** A shallow version would be exactly the kind of decorative feature CLAUDE.md rules out — a "strategy" that isn't actually grounded in real product/stock state isn't the thing the plan asked for, it's a fake version of it. The real version is a genuine schema change to a carefully-bounded pipeline (`payment_failures`/`recovery_attempts`, Layer 3's `chooseStrategy()` has an exhaustive `never`-typed switch specifically to make an ungrounded addition fail the build) — doing it properly is a task on its own, not a few hours tacked onto L6-5. The plan itself named this as the lowest-priority, first-to-cut task in the layer, explicitly ranking it below L6-4 (the offer/refusal log), which is done.
**Cost:** §5 idea #2 (Abandonment-to-Upsell Reframe) remains unbuilt. The seam it would attach to is real and unchanged: `product_variants` (with real stock) and the offer engine (L6-2) both already exist; the missing piece is solely linking a `payment_failures` row to what was being bought. Revisit as its own task if time allows — do not half-build it under time pressure.

### Refusals and deferrals counted, and shown, separately
**Context:** Layer 7's unified read layer draws from four sources — gate denials, risk escalations, offer-engine non-offers, and recovery-pipeline stops — and needed one headline number for the dashboard.
**Options:** One combined "refused" count across everything the system didn't simply allow; two separate counts (refusal vs. deferral) with the headline built from refusals only.
**Chose:** Two separate counts, kind: "refusal" | "deferral" as a first-class field on every unified decision, with deferrals (an escalation, or `recovery_escalated_to_human`) never counted as a refusal.
**Because:** An escalation is the system asking a human, not declining on its own — many escalations are later approved. Folding them into "refusals" would inflate the headline with decisions that were often reversed, and would blur exactly the distinction CLAUDE.md rule 2 asks this codebase to make visible: code enforces limits (refusals), a model's judgment sometimes asks for a human (deferrals). Keeping them separate is also what makes the "N of these were arithmetic, M involved a model" line on `/dashboard/explain` true rather than approximately true.
**Cost:** Two numbers to explain instead of one, and the dashboard has to spend a sentence distinguishing them rather than showing a single bigger, simpler-looking figure.

### The unified refusal read layer merges four independently-fetched, differently-shaped sources in code, not a single SQL UNION
**Context:** `getUnifiedDecisions()` needed one newest-first, paginated list drawn from `audit_log` (two different sub-cases — gate denials and risk escalations), `offer_decisions`, and `recovery_attempts`/`audit_log` again for recovery stops.
**Options:** A real `UNION ALL` across all sources with a shared column projection computed in SQL; four independent queries (each bounded by `limit`), merged and sorted in application code.
**Chose:** Four independent queries merged in code.
**Because:** The four sources don't share a row shape — `offer_decisions` has no `bound_applied` concept, `recovery`'s "bound" comes from parsing a fixed set of `stoppingRule` strings, and `risk_escalation`'s determinism has to be read off a reason-text prefix, not a column. Expressing that translation logic (the `BOUND_LABELS`/`RECOVERY_RULE_LABELS` maps, the recovery-arithmetic string parsing) inside a SQL `UNION` would mean either four near-identical `CASE` trees duplicated in SQL, or a database view that has to be migrated every time a new bound string appears — both worse for a codebase whose whole discipline is "an unmapped bound must render visibly, not silently," which is far easier to guarantee and test in TypeScript than in generated SQL.
**Cost:** A `limit: N` fetch from each source, verified live, does not guarantee `N` real decisions after merge-and-filter if a source's raw rows include informational (`n/a`-decision) noise the code then drops — this is exactly the bug FAILURES.md records for this layer (the initial `!= "allow"` filter). The fix was tightening the SQL predicate per source to match the code's own definition of "a decision," not switching approaches — but it's a class of bug a real `UNION` with a single shared `WHERE` wouldn't have been as easy to get wrong per-source, so the tradeoff is real, not free.

### A generated decision explanation is never persisted, and is not authoritative
**Context:** L7-4's decision explainer produces a plain-language paragraph from a recorded decision's real fields, via `completeStructured`.
**Options:** Cache the generated explanation on the decision (a new column on `audit_log`/`offer_decisions`, or a side table) so it's stable and doesn't require a fresh model call every time a merchant reopens the row; generate on demand, every time, and never store it anywhere.
**Chose:** Generate on demand, discard after rendering.
**Because:** The recorded `reason` is the record CLAUDE.md rule 1 requires — a judge, or a merchant, reading it later must see what was actually written at decision time, not a plain-language gloss that could theoretically diverge from it (a different model, a prompt change, or the same model phrasing the same facts slightly differently on a later call). Persisting a generated explanation risks it being mistaken for, or silently drifting from, the authoritative reason. Generating fresh every time keeps the boundary CLAUDE.md rule 2 draws — "explaining a decision" is LLM-appropriate, but the explanation must stay visibly downstream of the recorded fact, never a second copy of it.
**Cost:** No historical record of what a merchant was actually shown when they clicked "explain" on a past decision — if the wording mattered later (a dispute, a review), it can't be reconstructed, only regenerated (possibly differently). A repeat "explain" click on the same row also costs a fresh model call rather than being free the second time.

### The decision explainer's grounding is real but not airtight — a right number in a wrong sentence is still possible
**Context:** L7-4 needed the explainer to never invent a number, following the isolated-SYSTEM-FACT pattern `chat.ts` already uses (and the bug FAILURES.md records that pattern was built to fix).
**Options:** Trust the isolated-fact-line prompting alone; additionally verify post-hoc (regex-extract every number the model's output contains and check it against the supplied facts) and reject/retry on a mismatch; both, but state the honest limit rather than claiming certainty.
**Chose:** The isolated-fact prompting, verified in tests that every number in a real generated explanation traces back to a supplied fact — but no runtime post-hoc rejection, and an explicit acknowledgment that this guards against invented numbers, not against a correct number attached to an incorrect claim (e.g. "denied because the cap was exhausted" when the real bound was the per-transaction ceiling).
**Because:** A runtime reject-and-retry loop on number mismatch adds real latency and complexity to a feature whose whole value is being a lightweight reading aid, for a failure mode the recorded `reason` already fully covers — the generated text is always shown alongside the verbatim recorded reason, never in place of it, so a subtly-wrong gloss is checkable by the reader in the same view. Over-engineering the grounding guarantee here would spend effort disproportionate to what's actually at risk.
**Cost:** A merchant who reads only the generated paragraph, not the recorded reason next to it, could occasionally be told a technically-correct-sounding but structurally-wrong story about a decision. The UI mitigates this by always showing the recorded reason as primary and the explanation as a clearly-labelled secondary aid, but a determined user could still skip straight to the gloss.

### How an agreed negotiated price is represented and redeemed
**Context:** Layer 8 needs a buyer to pay an amount that was reached in a conversation, not a merchant-authored-in-advance catalogue price or bundle discount. The gate's `product_price_match`/`offer_price_match` bounds already proved the pattern for a fixed price: a caller references a merchant-authored row by id, the gate independently re-derives the amount and denies on mismatch. The question was whether to reuse the existing `offers` table (which already has a working redemption path) or build a parallel one for negotiated prices.
**Options:** (a) make `offers.bundleId` nullable and add a nullable `negotiationId`, so one table carries both kinds of discount; (b) create a real one-item `bundles` row for every agreed negotiation, so a negotiated price literally is a bundle; (c) a separate `negotiations` table with its own resolver (`resolveNegotiation`) and its own gate bound (`negotiation_price_match`), mirroring `offer_price_match` exactly, with the negotiation row itself doubling as the redeemable artifact once `status` reaches `agreed` (no third, separate "agreed price" table).
**Chose:** (c). `negotiations` carries the full lifecycle (open, agreed/refused/expired, redeemed) and, once agreed, is directly what a purchase resolves against — `agreedUnitPricePaise` is null until that transition and never written any other way.
**Because:** A negotiated price and a bundle discount are genuinely different things — different bounds (a bundle has a max-discount-percent off a catalogue sum; a negotiation has a per-variant floor and a turn budget), different provenance (merchant-authored in advance vs. reached live in a conversation), and a different audit story (a bundle is a catalogue artifact, a negotiation is a transcript). Option (a) would have made `offers` a two-shape table with a nullable FK that rots the moment a third discount kind appears; option (b) would have been a lie in the data model — a merchant's real bundle list filling with machine-generated single-item "bundles," and `createBundle()`'s discount-percent check either bypassed or double-applied with a different meaning. Layer 5-1 and Layer 6-1 both chose "a new column, never repurpose an existing one" for the identical reason (`money_actions.variantId` alongside `productId`, `offerId` alongside both) and both were right.
**Cost:** More code than either alternative — a second redemption path (`resolveNegotiation` alongside `resolveOffer`) with its own gate bound and its own `MoneyActionRequest.negotiationId` field, and every surface accepting `offerId` (the storefront's `BuyButton`, `/api/checkout/order`, the MCP `purchase` tool) needed the identical extension for `negotiationId`. `checkBounds` also had to add an explicit mutual-exclusivity check across `variantId`/`offerId`/`negotiationId`, denying a request that names more than one as ambiguous rather than resolving it by precedence.

### The negotiation floor is a merchant-authored price, not a margin derived from cost
**Context:** A negotiation that refuses below a floor and agrees above it leaks the floor's location by construction: a buyer who counters ₹800 (refused) then ₹850 (agreed) has just binary-searched the floor to within ₹50, in two turns. If that floor were computed from `product_variants.costPaise`, the buyer would have learned the merchant's actual cost — a far more sensitive number than a stated minimum price.
**Options:** Derive the floor at negotiation time from `costPaise` plus a merchant-set minimum margin percent; add a dedicated `floorPricePaise` column the merchant sets directly, checked against `costPaise` only at write time (with an explicit `belowCostFloorAcknowledged` override, mirroring `bundles.belowCostAcknowledged`); both.
**Chose:** A dedicated `floorPricePaise` on `product_variants`, merchant-set directly, never recomputed from cost at negotiation time. Combined with capping counter-offers at `MAX_BUYER_COUNTERS` (3) as an anti-probing bound in its own right — three turns is not enough to binary-search a floor to a useful precision even against a stated price, let alone a derived margin.
**Because:** This makes the thing a buyer can ever learn by probing "the merchant's stated minimum for this item," never "the merchant's cost or margin" — a real, meaningful difference for a merchant's business. It also happens to be the version a real merchant can actually use: "never sell this below ₹800" is a sentence a merchant states directly; "maintain a 22% margin on this negotiation" is one they'd have to compute from a cost figure they may not want to expose column access to in the first place. `null` means "not negotiable at all," the same "absence is real, never a permissive default" discipline `merchant_policies`/`merchant_reward_settings` already use.
**Cost:** A merchant sets one more number per variant they want negotiable, and nothing in this layer enforces the floor stays a sane percentage of the catalogue price beyond the existing below-cost acknowledgment — a merchant could set a floor at ₹1 on a ₹10,000 item, and the system will honour it exactly as stated. That is treated as a legitimate merchant decision (the same reasoning `bundles.belowCostAcknowledged` already accepts for a deliberate loss-leader), not a bug to guard against.

### The merchant's counter price is deterministic, computed by code, and the model is never asked to choose a number
**Context:** L8-2's engine needs the merchant's agent to counter a below-floor offer with something. The obvious design — ask the model to propose a counter within an allowed range — still leaves the model as the thing that chooses the actual number a buyer sees, even if the range is code-bounded.
**Options:** Hand the model a floor-safe [min, max] range and let it pick a price within it, re-validating and clamping the result afterward; compute the exact counter price in code first (`computeConcessionCeiling` — an even split of the remaining gap across the turns left in the budget, converging exactly to the floor by the final turn), and ask the model only to phrase that already-decided number as a sentence.
**Chose:** The second. `submitBuyerCounter` reassigns `counterPricePaise` from the code-computed `ceiling` unconditionally, on the line immediately after the model call returns — there is no code path, adversarial or otherwise, by which the model's response can influence the number.
**Because:** "Re-validate and clamp a model-chosen number" is still a design where the model's job includes choosing a price, and a validation bug (an off-by-one in the clamp, a missed edge case) would be a real vulnerability in the single most safety-critical number in this layer. "The model never produces the number at all" removes that class of bug entirely rather than defending against it — the concrete difference between an architectural guarantee and a well-tested one. This mirrors L6-2's margin filter precedent (a below-floor bundle is structurally excluded from the model's input, not merely discouraged by a prompt) applied one step further: here, the model's output physically cannot reach the number at all, not just the input.
**Cost:** The model's contribution to a countered turn is purely cosmetic (word choice), which is a narrower use of the LLM than the plan's own framing ("a model may argue") might suggest — the model does not actually argue for a different number, only phrases the one code already picked. This is a deliberate, conservative interpretation of "argue," chosen because CLAUDE.md rule 2's bar ("where you chose not to use AI") is explicitly graded, and the safest place to under-use a model in this codebase is the one number a buyer will actually pay.

### `negotiations.status` has one terminal refusal value, not two
**Context:** The initial schema included both `refused_floor` and `refused_turns_exhausted` as distinct terminal states, anticipating a meaningful difference between "the buyer's offer was hopelessly below the floor" and "the negotiation was making progress but ran out of rounds."
**Options:** Keep both and invent a heuristic distinguishing them (e.g. whether the gap was closing turn over turn); keep both but only ever write one, leaving the other permanently dead; collapse to a single status, since the actual code (`submitBuyerCounter`) only ever has one way to end a negotiation without agreement — the turn budget runs out while still below the floor.
**Chose:** Collapse to one status, `refused_turns_exhausted`, removed via a real migration (verified zero rows used the dropped value in the live database before dropping it).
**Because:** `submitBuyerCounter` never gives up early — every below-floor counter gets another round until `MAX_BUYER_COUNTERS` is exhausted, so "gave up below the floor with turns still remaining" is not a state the code can actually reach. Inventing a heuristic to justify a second status would have been exactly the kind of decorative distinction CLAUDE.md warns against: a difference that exists in the schema but isn't backed by a real code path. A dead enum value that nothing ever writes is worse than no distinction at all, since it invites a future reader to assume it means something.
**Cost:** None identified — a merchant reading `/dashboard/negotiations` sees one refusal reason ("no agreement within the turn limit") rather than two, which is an honest simplification, not a loss of real information: the exact buyer counter and turn count are still shown either way.

### L8-5 (dead-stock liquidation) cut, not built
**Context:** The Layer 8 plan's L8-5 asked for the merchant-initiated inverse of buyer-driven negotiation — the merchant's agent identifying slow-moving stock and opening negotiation proactively (prd.md §4 idea #3). The plan itself named the honest constraint up front: "slow-moving" needs real sales history to mean anything, and explicitly said to cut the task rather than fabricate a staleness score if the seeded catalogue doesn't have enough. Checked directly against the real database before writing any code: the real seeded merchant has exactly 7 `money_actions` rows total across its entire lifetime (6 captured/executed), spread across a real multi-week build history.
**Options:** Build a "no sale in N days" signal anyway, on that thin a history; invent a synthetic staleness score from `stock`/`createdAt` alone, without real purchase data backing it; cut the task, following the plan's own explicit instruction and L6-6's precedent for doing this honestly.
**Chose:** Cut, documented here rather than silently dropped — exactly the reasoning that already cut L6-6 (abandonment-to-upsell) in Layer 6.
**Because:** With 6 real purchases spread across the whole catalogue's lifetime, any "slow-moving" signal computed from this data would be indistinguishable from noise — every variant would look equally "slow," which isn't a real signal, it's the absence of one dressed up as arithmetic. Building a feature that runs code over real rows but produces a meaningless answer is worse than not building it: it looks evidence-based to a judge or a merchant while actually being decorative, which is precisely what CLAUDE.md rules out.
**Cost:** §4 idea #3 (Dead-Stock Liquidation Negotiator) remains unbuilt. The seam it would attach to is real and complete: `negotiation.ts`'s engine (the floor, the concession schedule, the turn budget) works identically regardless of who opens the negotiation, and `product_variants.stock`/`createdAt` both already exist. The only missing piece is a real distribution of purchase history to compute staleness from — revisit if the product ever has one, not before.

## Layer 9 — the interface and project close-out

### Design character, palette, and typography for the design system (L9-1)
**Context:** Every dashboard page before this layer used raw Tailwind defaults with no design system — `border rounded-lg p-4`, `bg-blue-600`, and `font-family: Arial, Helvetica, sans-serif` in `globals.css`'s body rule (a bug in its own right: it silently overrode the Geist font `layout.tsx` was already loading via `next/font`, so the correct font was configured but never actually applied). The product needed one committed visual identity before any page could be redesigned, or eleven pages would each invent their own.
**Character:** Calm, precise, slightly severe — a system that is clearly counting, and clearly willing to say no. Every token below traces back to that sentence: cool, low-saturation surfaces (calm); tabular mono figures and a small type scale (precise); a narrow, deliberate accent used only where something is actionable (severe, not decorative); the allow/deny/escalate triad as the palette's real spine (a system built to say no).
**Options considered for the palette:** Match Razorpay's own brand blue (`#012652` navy / `#0D94FB` dodger blue) directly, for immediate visual association; use a generic dark-SaaS palette (indigo/violet on near-black, the default output of most AI design tools); build a palette shifted away from Razorpay's hue with the merchant's actual decision semantics (allow/deny/escalate) as its structural basis.
**Chose:** The third. A deep, cool-neutral ink (not navy, not warm like payloadservice's amber-brown reference) as the base surface, with the allow/deny/escalate triad — not a single generic accent — doing the real semantic work, and one narrow accent hue reserved for "this is actionable right now."
**Because:** Cloning Razorpay's own blue on a product built *for* Razorpay merchants risks reading as an official Razorpay product or a cheap knockoff, neither of which this project should claim. An indigo/violet dark-SaaS default is the single most-cited "AI slop" tell in the design research done for this layer (the "AI Purple Problem") and this project explicitly wants to not look default-generated. The decision triad already exists as a closed enum in the schema (`money_actions.status`/audit `decision`) and is the actual content of the product — building the palette around it means the interface states what the system does before a word is read, for free.
**Cost:** A palette with three semantic accents plus one action accent needs real discipline to keep from feeling busy; the rule enforced throughout L9 is that the decision colours only ever appear on decision badges/streams, never as generic UI decoration elsewhere on the page.

### Typography: a display face with real character, a small-size-literate UI face, and mono tabular figures on every number (L9-1)
**Context:** `next/font` was already correctly wired (self-hosted Geist Sans/Mono, zero layout shift) but never actually reached the page, because `globals.css`'s `body` rule hardcoded `font-family: Arial, Helvetica, sans-serif` over it. Beyond fixing that bug, Geist Sans alone is also, by the design research's own findings, one of the most common default faces in AI-generated interfaces (alongside Inter) — using it without a distinct display pairing would still read as a template default at large sizes.
**Options:** Keep Geist Sans/Mono only, correctly wired (fixes the bug, changes nothing about default-ness); add a distinct display face for headings while keeping Geist Mono for numbers; introduce a whole new pairing including a new body face.
**Chose:** Fixed the `body` rule bug first regardless. Added one display face with real character for headings/hero copy, kept Geist Sans for UI body text (it is genuinely good at small sizes, which is the harder-to-satisfy requirement for a dense dashboard), and made Geist Mono with tabular figures mandatory on every money amount, id, SKU, percentage, and count in the product — never a proportional sans for a number.
**Because:** The single highest-leverage typographic change for "looks like a real financial product" is right-aligned tabular-figure numbers, which is explicitly what makes Stripe's dashboard tables the category reference (per the design research done for L9-1) — cheap to apply everywhere and immediately legible as deliberate rather than default. A new display face at headline sizes is where a generic template most visibly announces itself, so that is the one place worth spending a genuinely distinctive choice; the UI body text needed to stay Geist Sans because rewriting every dense table's base font is a much larger, much riskier change for comparatively little visual payoff.
**Cost:** One additional font family loaded via `next/font` (self-hosted, same zero-layout-shift mechanism already in use — no new network origin, no CDN link tag).

### The landing hero's ambient backdrop is procedural, not a video file — and the "refusal" example is explicitly labelled illustrative
**Context:** The design research for this layer (plans/layer-9-interface-and-close.md fact 5) named an ambient background video — following `../payloadservice/src/components/Hero/Hero.tsx`'s pattern — as a strong reference for a non-generic, professional landing page. But payloadservice's actual video files are that project's own branded asset (an amber/indigo/sage/slate silk-fabric motif matching its specific identity), not something this product should reuse — a different company's footage on this product's landing page would be a real misattribution, not a shortcut.
**Options:** Source new stock/generated video footage matching this product's palette; ask the user where to find or how to source real footage; build the same ambient effect procedurally in canvas/CSS instead of shipping any video file at all.
**Chose:** Procedural — a canvas-driven drift of soft radial gradient blobs in the product's own decision-triad palette (`AmbientField`, `src/components/ui/ambient-field.tsx`), asked of the user directly as a real judgment call rather than assumed.
**Because:** It achieves the same ambient, non-generic effect the reference established, but is strictly better on every axis that matters here: zero binary asset weight (vs. payloadservice's already-deliberately-small ~85KB clips), zero licensing/attribution question, and it can render the product's actual semantic palette (the allow/deny/escalate/accent tones) rather than abstract footage of something with no relationship to the product. It also can never become an LCP risk, which a video always has some chance of being no matter how compressed.
**Cost:** A canvas animation has to be hand-tuned for "calm, not distracting" rather than benefiting from real footage's inherent visual richness; `prefers-reduced-motion` support had to be implemented explicitly (draw one static frame, stop) rather than relying on the `<video>` element's native pause-ability.

**Separately, the same landing page's "refusal as the hero feature" section** renders a real `gate.ts`-shaped denial (the exact reason-string format `product_price_match` produces, verified against the real template in `gate.ts` rather than invented prose) but explicitly labelled "Illustrative" in the UI, not pulled live from any real merchant's audit log. The public landing page has no authenticated merchant to scope a real decision to, and displaying a specific real merchant's actual business data (even a denial, even anonymized-looking) on an unauthenticated public page would be a privacy problem this project's own multi-tenant isolation discipline exists to prevent — see DECISIONS.md's and FAILURES.md's repeated `audit_log.merchant_id` cross-tenant-leak lesson. Fact 9's "nothing renders that didn't really happen" rule is honored here at the level that actually matters: the *shape* and *mechanism* of the refusal is completely real and verified against the live code, only the specific numbers in this one public-marketing instance are a labelled example rather than one particular merchant's private figures made public without consent.

### L9-8 (§6 #1, Referral Instant-Payout Agent) cut, not built
**Context:** The Layer 9 plan named this the one §6 idea worth building if L9-1 through L9-4 landed solidly (they did), explicitly requiring a pre-flight check: real payout execution needs Razorpay Payouts (RazorpayX), and the plan said to verify that's actually available before designing anything, with an explicit instruction that an unavailable Payouts API means building the honest gated-but-not-executed version, or cutting outright.
**Options:** Check whether this project's Razorpay test-mode credentials/SDK version support Payouts and build the real thing; build a "recorded, gated, audited payout obligation" that never actually transfers money, with that limitation stated plainly; cut it, following the same reasoning that already cut L6-6 and L8-5.
**Chose:** Cut. The installed `razorpay` SDK (checked directly — `node_modules/razorpay/dist/types/`) has no Payouts API surface at all, only Settlements; RazorpayX Payouts is a distinct product requiring separate partner approval this project was never given (the same category of gap DECISIONS.md already records for the Razorpay OAuth "Connect Razorpay" flow). Building the "gated but not executed" half-version was considered and rejected: with no real transfer mechanism reachable at all, that version reduces to writing rows to a table and calling it a feature, which is precisely the demo-shaped decoration CLAUDE.md and this project's own L8-7 audit task exist to remove — it would look evidence-based on a pitch slide while doing nothing a real merchant could use.
**Because:** This project is already large — nine layers, ~230 tests, a real MCP server, a real negotiation engine with a provably unbreakable floor, real recovery via genuinely payable Payment Links, and (this layer) a from-scratch design system across every surface. CLAUDE.md is explicit that two complete layers beat eight half-built ones, and Layer 9's own plan named this task "the first thing to cut" in the same breath as introducing it. Spending remaining Layer 9 time on the interface work already in flight (L9-9's close-out verification, in particular) is a better trade than a payout feature this codebase has no real mechanism to execute.
**Cost:** prd.md §6 idea #1 remains unbuilt, alongside #2-#5 (already not attempted per the Layer 9 plan's own "What §6 actually gets" section). The seam is real and cheap to pick up later if RazorpayX access is ever granted: a referral code is deterministic string-matching (no model needed, matching every other bound in this codebase), and the payout itself would be one more `attemptMoneyAction()` call site with its own ceiling/threshold bounds, following the exact pattern every other money-moving feature in this project already uses.

### A genuine multi-item cart is one gate purchase target, not per-line checkout calls
**Context:** After Layer 9's UI pass, the buyer chat's cart was still the single-line placeholder Layer 5-7 shipped (`conversations.cartProductId`/`cartVariantId`/`cartQuantity`) — a real functional gap, not a styling one: a buyer could never hold two different products in the cart at once. Closing it meant a real design choice about how checkout should treat multiple lines.
**Options:** (a) Keep the cart multi-line in the chat's own state but check out one line at a time, reusing the existing single-`variantId` `attemptMoneyAction` path N times; (b) build a genuine multi-item order — one gate call, one Razorpay order, one `money_actions` row, covering every line at once.
**Chose:** (b), asked of the user directly since it's a real product-shape decision with different schema/gate implications, not a default to assume. `gate.ts` gained a 14th contract point mirroring point 13 (a negotiated price) and, structurally, Layer 6's offer/bundle machinery: `MoneyActionRequest.cartConversationId` names a conversation, `cart.ts`'s `resolveCartForCheckout()` re-derives the total fresh from every `cart_items` line's live price and stock, and stock reservation reuses `reserveOfferStock`/`releaseOfferStock` (already all-or-nothing and multi-item) unchanged.
**Because:** Option (a) would have been a UI-only illusion of a cart — the chat widget could *show* two lines, but "buying the cart" would silently become two separate orders, two separate audit entries, and two separate agent-consent decisions for what a buyer experiences as one purchase. That's the exact kind of surface-level fix CLAUDE.md's "real product, not a demo" standard exists to catch. A real multi-item order is also barely more code than the fake version: `bundle_items`/`reserveOfferStock` already proved the pattern (a set of variant/quantity lines, one price, one atomic reservation) in Layer 6 — a cart is structurally that same shape, just buyer-authored and ad-hoc instead of merchant-authored and fixed-price, so it slotted into the gate's existing `offer`/`negotiation` dispatch pattern almost mechanically.
**Cost:** `money_actions.cartId` can't point directly at the live, buyer-editable `cart_items` rows (a buyer keeps shopping after checkout, so those rows change), so a purchase needs its own frozen record — new `cart_purchases`/`cart_purchase_items` tables, a snapshot written the moment stock reservation succeeds, mirroring why `negotiations` freezes `catalogueUnitPricePaise` at open time rather than re-reading `product_variants` later. The agent-facing purchase API (`/api/agent/purchase`, the MCP `purchase` tool) deliberately was **not** extended to accept a cart — an autonomous AI buyer making N separate, independently-gated, independently-audited purchase calls is the more honest and auditable pattern for a headless caller than bundling multiple decisions into one opaque request; the cart concept is specifically a human browsing-then-committing UX affordance for the chat/storefront flow, not something the agent API needs.

### Multi-variant product management, closed rather than left as a documented gap
**Context:** Every prior layer's dashboard products page (`/dashboard/products`) managed exactly one variant per product — the "fast path" comment in the code explicitly named managing a second variant (a different size, a different colour) as a real, unclosed gap, deferred to "see plans/layer-5-agent-readable-catalog.md."
**Options:** Leave it as a documented gap (the schema already supported multiple variants per product — `product_variants.productId` is a real one-to-many — only the dashboard UI never exposed it); build a full variant-matrix editor; build a simpler "add one more variant" affordance without a matrix.
**Chose:** The simpler affordance — asked of the user directly which register to build to, and confirmed "full variant management," not the minimal option. `dashboard-mutations.ts` gained `addVariant`/`updateVariant`/`archiveVariant`/`reactivateVariant`, each independently merchant-ownership-checked the same way `updateProduct` already was; `/dashboard/products` renders a per-variant row (price/stock/SKU/attributes, its own Edit form and Archive/Reactivate button) whenever a product has more than one variant, and an "Add a variant" form on every product.
**Because:** The underlying schema and every read path (`getPublicCatalogue`, the MCP catalogue tool, the agent-facing product API) already fully supported multiple variants per product since Layer 5-1 — only the merchant's own ability to *create* a second variant was missing. That is exactly the same class of gap Layer 5-1's own `createProduct` closed for a product's first variant ("before this task, `scripts/seed.ts` was the only way one ever existed"): a real merchant cannot be expected to hand-edit the database to list a second size of the same coffee.
**Cost:** No true variant "matrix" UI (bulk-editing many attribute combinations at once, e.g. every size × roast pairing for one product in a single form) — each variant is still added and edited one at a time. For the realistic case (a merchant occasionally adding a second or third size/colour to an existing product), one-at-a-time is not a meaningful limitation; a true matrix editor would be building for a scale of catalogue complexity this project has no evidence any real merchant here needs yet.

### Product renamed Northside → ThirdMan
**Context:** The user chose a real product name — ThirdMan, evoking the platform's actual role as the trusted third party standing between an AI buyer and a merchant — to replace the placeholder "Northside" brand used throughout Layer 9's design work.
**Options:** A pure find-replace across every string; or a scoped rename that separates the platform's own brand from the seeded demo merchant's in-universe business name ("Northside Coffee Supply Co."), which happens to share the old word but is a different kind of string entirely — a DB lookup key with real accumulated seed history (money_actions, audit trail), not platform branding.
**Chose:** Scoped. Changed exactly five user-facing strings: `layout.tsx`'s title/template, `opengraph-image.tsx`'s alt text, and the wordmark text in `sidebar-nav.tsx`/`login/page.tsx`/`signup/page.tsx`. Left `scripts/seed.ts`'s `MERCHANT_NAME`/`MERCHANT_EMAIL` and DEMO.md's `northsidecoffee.test` credential reference untouched — asked the user directly rather than silently deciding, and confirmed leaving the seed merchant's business name as-is.

### Landing page layout bugs fixed, real asymmetry added — not a redesign
**Context:** The user reported the landing page "totally broken" (a screenshot showed a large empty gap above the hero and a badge pill overlapping a text label) and separately flagged it as "vibecoded" — two different claims requiring two different diagnoses before touching anything.
**Options for the "broken" claim:** Guess at a fix; or read the actual code and isolate the precise bugs before changing anything.
**Chose:** Isolated three real, specific bugs by reading `src/app/page.tsx`/`globals.css`/`reveal.tsx` directly: (1) the "Illustrative..." label + "Denied" badge row (page.tsx ~74-81) had `flex items-center justify-between` with no `flex-wrap`, no `min-w-0` on the label, no `shrink-0` on the badge — a genuine overflow/overlap bug at narrower widths, fixed by adding exactly those three things, not a broader restructure. (2) The hero's `[data-rise]` elements (the eyebrow, H1, lead paragraph, CTA row) started at `opacity: 0` and only became visible once `Reveal`'s `IntersectionObserver` fired client-side after hydration — a scroll-reveal pattern applied to content that's already inside the initial viewport isn't revealing anything on scroll, it's just an artificial opacity delay on the very first thing a visitor sees. (3) The hero section used `flex flex-col justify-center` on a `min-h-[92svh]` container — true vertical centering, which makes the empty space above the headline a direct function of viewport height and reads as an accident rather than a decision on a short/wide window. Changed to `justify-start` with a `clamp(6rem,18vh,10rem)` top offset — a controlled, designed gap regardless of viewport height.
**Options for the "vibecoded" claim:** Assume it and redesign from scratch (new palette, new fonts, new component library); or audit the actual design system against a real checklist of what makes AI-generated UI look generic before deciding what to change.
**Chose:** Audited first. Found this codebase already avoids nearly every classic tell — no purple/indigo gradient, no glassmorphism, no emoji-as-icons, no gradient text, a considered documented palette with the allow/deny/escalate triad as its real spine (not a single decorative accent), a real Fraunces/Geist type pairing, and components (`EmptyState`, `Stat`) with explicit anti-fake-data discipline already built in. The two genuine gaps found: everything on the landing page was centered/stacked/symmetric with no real visual hierarchy beyond font size, and every section shared identical `--section-y` padding regardless of content importance. Fixed both without touching the palette, fonts, or component vocabulary: the hero gained a right-aligned `DecisionBadge` cluster (the three real semantic states, reused verbatim from the dashboard's own component, as a compositional device breaking the single-column symmetry — not new claims or fabricated data); the refusal-example section (the product's strongest content) got `1.15×` its neighbors' vertical padding, scaling the existing `--section-y` token rather than inventing a new one; the three-surfaces grid became asymmetric (`lg:grid-cols-[1.3fr_1fr_1fr]`) with the Agent API card — the single most load-bearing claim — spanning wider with a larger heading; both auth pages gained a low-opacity `AmbientField` backdrop (reused unchanged) so they read as the same front-door register as the landing page instead of a bare centered-card template.
**Considered and rejected:** A real `DecisionComposition` stat bar on the landing page as social proof, sourced from a platform-wide `audit_log` aggregate. Checked live against the dev DB: 46 allow / 142 deny / 16 escalate — but across 99 total merchant rows, almost all created and destroyed by automated test runs, not real usage. Technically a real query result, but not honest evidence — shipping it would misrepresent test-suite noise as merchant activity, the same category of problem the "Illustrative" labelling on the denial example exists to avoid. Asked the user directly; skipped the stat bar entirely rather than fabricate a number or ship a misleading real one.
**Because:** The user's two complaints had different root causes and needed different remedies — the "broken" report was a real, fixable CSS/markup bug (three of them, specifically), and the "vibecoded" report, on audit, was mostly not present in this codebase already; the actual gap was a lack of deliberate asymmetry, not the wrong palette or a generic component library. Redesigning from scratch would have thrown away a genuinely well-considered design system to fix problems that weren't there, while leaving the real overlap bug unaddressed if the effort went into a new palette instead of the actual broken flex row.
**Cost:** None identified — every change reuses existing tokens/components, verified via `tsc --noEmit`/`eslint`/`npm run build` all clean, and the fixed HTML confirmed live against the running dev server (data-rise count dropped by exactly four in the hero, the overlap-fix classes present, the asymmetric grid template present, ThirdMan present with zero Northside references in the rendered output).

## Layer 10 — the embeddable widget

### Cross-origin iframe on this app's own origin, not injecting DOM into the host page

**Context:** L10-2 needed a way to put the buyer chat on a merchant's own third-party site via one `<script>` tag. Two ways to do this: inject the widget's markup directly into the host page, or mount it inside an `<iframe>` pointing back at this app.

**Options:** DOM injection — the loader script builds the chat UI directly in the merchant's document, using inline styles or a scoped stylesheet since the host page has no `globals.css`; or a cross-origin iframe — the loader injects a launcher button plus an `<iframe>`, and the real `ChatWidget` component renders on this app's own origin inside it.

**Chose:** the iframe. `ChatWidget` gained a `variant: "floating" | "embedded"` prop instead of a second, framework-free reimplementation.

**Because:** `chat-widget.tsx` is 290+ lines of React bound to this app's Tailwind design tokens (`bg-ink-raised`, `--radius-lg`, the decision-triad palette), and `buy-button.tsx` injects Razorpay's real `checkout.js` and drives a real Checkout modal. Reimplementing either framework-free would create a second, parallel implementation of every buyer-facing surface — cart, negotiation, offers, checkout — that would immediately start drifting from the first (a bug fixed in one would silently not apply to the other). An iframe on this app's own origin gets the real design system, real components, and real Checkout flow for free, with total style isolation as a side effect, and turns "the host page needs to know what happened" into an explicit `postMessage` protocol (L10-4) rather than something to invent separately.

**Cost:** an extra document load per embed, and the iframe's `sandbox`/`allow` attributes have to be exactly right or Razorpay Checkout's UPI/netbanking/3DS popups silently fail to open — verified against a real test payment inside a real iframe, not inferred (`sandbox="allow-scripts allow-forms allow-same-origin allow-popups allow-popups-to-escape-sandbox"`, `allow="payment"`).

### The embed key travels as a request header, not a JSON body field

**Context:** L10-3's origin-enforcement layer needs to resolve which merchant a cross-origin request belongs to before deciding whether to allow it — including during a browser's CORS preflight (`OPTIONS`), which happens before the real `POST`.

**Options:** Put the embed key in the JSON request body, alongside `merchantId` and everything else the existing (pre-Layer-10) routes already took; or send it as a dedicated `X-Embed-Key` request header.

**Chose:** a header, after building the body-based version first and catching the bug it caused via a real `curl`-driven preflight (not a unit test — the unit tests all passed with the broken version, since none of them exercised a genuine bodyless `OPTIONS` request).

**Because:** a real browser CORS preflight carries **no body** — only the method and headers it announces via `Access-Control-Request-Method`/`-Headers`. A body-only embed key is therefore invisible to `embed-cors.ts`'s preflight handler no matter how it's written; the preflight can never determine whether to allow the origin, so a real browser would fail every cross-origin embed request even though the same request curled directly (bypassing the browser's own preflight) would succeed. See FAILURES.md for the specific bug and how the `curl -X OPTIONS` test caught it.

**Cost:** none identified — the header is simpler than the body-based version was (the preflight handler no longer needs a per-route `extractMerchantId` callback to peek at the body, since the key alone already names one merchant).

### Publishable key stored in plaintext, shaped so it can never be mistaken for an agent secret key

**Context:** the embed's key lives in public HTML (`<script data-embed-key="...">`), viewable by anyone via view-source. This is a fundamentally different trust level than an agent's API key, which authenticates a server-side AI buyer and is genuinely secret.

**Options:** Reuse `agents`' existing `sk_`-prefixed, SHA-256-hashed key scheme for the embed too; or introduce a separate, differently-shaped key.

**Chose:** a new `pk_`-prefixed key (`embed.ts`'s `generatePublishableKey()`), stored in **plaintext** in `embed_configs.publishable_key`, with `assertNotSecretKey()` rejecting an `sk_`-shaped value wherever a `pk_` is expected.

**Because:** hashing a value that is printed verbatim into public HTML by design buys nothing — anyone who wants the key already has it from view-source. Storing it in plaintext is what lets `/dashboard/embed` show a merchant their own current key again after a page reload, the opposite of `agent-key-reveal.tsx`'s deliberate "shown once, then genuinely forgotten" contract for a real secret. The distinct `pk_`/`sk_` prefixes and the `assertNotSecretKey()` guard exist specifically against the failure mode of a merchant pasting an agent's real secret key into their own public HTML, or a future contributor assuming the two schemes are interchangeable.

**Cost:** two key schemes to keep straight in the codebase instead of one — mitigated by the prefixes being load-bearing (checked in code, not just convention) and by both `embed.ts` and `agent-auth.ts` cross-referencing each other in comments.

### The publishable key does not authenticate the embed — it shares the storefront's existing hidden agent

**Context:** the gate requires an `agents.id` for its bound checks (spend cap, status) on every purchase. The embedded widget needed a way to satisfy that without holding an agent's secret key in the browser.

**Options:** Give the embed its own hidden agent and spend cap (`__embed_checkout`, mirroring `storefront.ts`'s `getOrCreateStorefrontAgent` pattern but as a second instance); or have it share the exact same hidden `__storefront_checkout` agent `/store/[merchantId]` already uses.

**Chose:** share the same agent and cap. `getOrCreateStorefrontAgent()` is called unchanged from `/api/checkout/order` regardless of whether the request came from the embed or the storefront page.

**Because:** the embed calls the identical public buyer endpoints the storefront already calls, with identical trust properties (unauthenticated, bounded by a real spend cap either way) — a leaked publishable key gets an attacker at most what visiting the merchant's public storefront already gets them. Building a second hidden agent speculatively, before any merchant has asked to bound their website's spend separately from their storefront page's spend, would be exactly the kind of unrequested abstraction CLAUDE.md's working agreement warns against.

**Cost:** a merchant cannot currently see "how much did my own website's purchases spend" separately from "how much did my ThirdMan store page spend" in the audit trail — both draw from the same cap and the same hidden agent. The money action's `context` string does carry `(embed: <hostname>)` for forensic purposes, so the distinction is visible per-row even though the cap itself is shared. If a merchant needs the caps split, that is a real, well-understood follow-up (a second hidden agent, same pattern) — not built here.

### No wildcard support in the origin allowlist

**Context:** `embed.ts`'s `isOriginAllowed()` needed a matching rule for `embed_configs.allowed_origins`. A merchant with several subdomains (e.g. `shop.example.com`, `checkout.example.com`) might want to register them all at once with a pattern like `*.example.com`.

**Options:** Exact-origin matching only; or support a single leading-`*.` wildcard with a real dot-boundary check (so `evilexample.com` cannot match `*.example.com`).

**Chose:** exact origins only, no wildcard.

**Because:** a wildcard is real additional surface — a suffix-check implementation that gets the dot-boundary wrong is a genuine security bug (`evilexample.com` matching `*.example.com`), and building it half-verified would be worse than not having it. A merchant with three subdomains can list three exact origins; the allowlist editor on `/dashboard/embed` is a plain textarea, one origin per line, so this costs the merchant a few extra lines of text, not a blocked capability.

**Cost:** a merchant with many subdomains has more to type and more to keep in sync if a subdomain is added later. Acceptable for the common case (one or two origins); worth revisiting if a real merchant reports needing more.

### The outbound webhook runner needs a real external scheduler — wired into the shared cron endpoint, not a bespoke trigger

**Context:** L10-5's durable delivery queue (`webhook_deliveries`) needs something to actually call `drainDueDeliveries()` on a schedule. This stack has no always-on background worker process anywhere in it.

**Options:** Build a minimal in-process scheduler (a `setInterval` in the Next.js server process); rely on an opportunistic drain triggered by dashboard page loads (the same shape `escrow.sweepExpiredHolds()` uses on `/dashboard/escrow`); or wire into a protected, externally-triggered route.

**Chose:** the latter — `webhooks/runner.ts` exports `drainDueDeliveries()` as a plain function with no trigger of its own, and Layer 11's `POST /api/cron/run` (built concurrently on this same branch — see its own docstring) calls it via a dynamic `import()` guarded in a `try/catch`, alongside its own escrow/offer/escalation/restock sweep jobs. Confirmed live: `curl -X POST /api/cron/run` with the real `CRON_SECRET` returns `{"job":"webhooks:drain","ok":true,...}` in its job list.

**Because:** a `setInterval` inside a serverless/edge-deployed Next.js process is not reliable — the process isn't guaranteed to stay warm, and a missed interval silently delays delivery with nothing surfacing the fact. An opportunistic dashboard-triggered drain alone is a demo answer: a merchant who never opens `/dashboard/embed` gets no deliveries, defeating the entire point of a webhook. Two features on the same branch independently arriving at "this needs one shared scheduled entrypoint, not a bespoke trigger per feature" and converging on the same route is the right outcome — `webhooks/runner.ts` stays trigger-agnostic (any caller can drain it, including a test) and the actual production trigger (Vercel Cron pointed at `/api/cron/run`) is owned in exactly one place.

**Cost:** in a deployment where nobody has pointed a scheduler at `/api/cron/run` yet, delivery latency is unbounded (rows stay `pending`, nothing lost) — a real deployment step, not a code gap, and documented as such.

## Layer 11 — notifications, contactable customers, and token rewards

### A second delivery table (`notification_deliveries`), not reusing `webhook_deliveries`

**Context:** L11-2 needed a durable outbound queue for human-facing email, and L10-5's `webhook_deliveries` (built concurrently on the same branch) already establishes almost the identical shape — a row written before any attempt, a pure backoff `policy.ts`, retryable-vs-terminal classification, a partial-unique-index dedupe.

**Options:** Reuse `webhook_deliveries` with a `recipientKind`/`channel` discriminator column covering both a merchant's server and a human's inbox; or build a second, parallel table.

**Chose:** a second table, `notification_deliveries`, with its own `notifications/policy.ts`.

**Because:** the two recipients have genuinely different constraints that would otherwise all live behind `if (recipientKind === ...)` branches in every function. `webhook_deliveries` signs every payload with HMAC and validates against SSRF (a merchant-controlled URL is the risk); `notification_deliveries` has no signing at all and instead enforces consent (`customer_contacts.unsubscribedAt`) and a per-contact daily frequency cap (a human's attention is the risk, not a server's availability). The retry schedules also genuinely differ — webhooks retry a machine, so 1m/5m/30m/2h/6h is reasonable; emailing a human on the same aggressive schedule burns free-tier provider quota on soft bounces for no benefit, hence email's slower 5m/30m/4h. Forcing one table to serve both would mean either bloating it with fields the other path never uses, or littering conditional logic through what should be two small, readable modules.

**Cost:** two schemas to keep mentally distinct, and two dedupe indexes instead of one. Worth it — a reader opening `notifications/policy.ts` never has to reason about SSRF, and a reader opening `webhooks/policy.ts` never has to reason about unsubscribe consent.

### Resend, with an honest console-log fallback when no key is configured

**Context:** L11-2 needed a real email provider. This has to work on a free tier, and the layer has to be demonstrable even before the user configures an API key.

**Options:** SendGrid, Mailgun, Resend, or building against raw SMTP.

**Chose:** Resend, with `notifications/provider.ts` falling back to a `console.log` provider when `RESEND_API_KEY` is unset.

**Because:** Resend's free tier (3,000/month, 100/day) sends from a shared `onboarding@resend.dev` address with **no domain verification required** — every competitor in this space (SendGrid, Mailgun) requires verifying a domain via DNS records before sending anything beyond a handful of test emails, which this project doesn't own one to do. Resend's API is a single authenticated POST, so no new SDK dependency was justified (CLAUDE.md's no-new-dependency rule) — `fetch` is enough. The console fallback is not a mock: every bound (the queue, the retry policy, suppression, the audit trail) genuinely exercises with it; the only thing that doesn't happen is a real inbox receiving mail, and the delivery row records which provider served it so the UI can say so honestly rather than claim "delivered."

**Cost:** 100 emails/day caps how far this can be load-tested for free; a real deployment past demo scale needs a paid tier or domain verification, same as any provider.

### One cron endpoint (`/api/cron/run`) draining every scheduled job, not a bespoke trigger per feature

**Context:** Three separate, unrelated needs converged on the same problem during this layer: L11-2's notification queue needs a drain, `escrow.sweepExpiredHolds()` was previously only triggered by a merchant opening `/dashboard/escrow` (a real gap — an expired hold nobody looks at never auto-refunds), and L11-7's escalation expiry needs a periodic check.

**Options:** Give each feature its own trigger (a dashboard-page-load hook per feature, matching escrow's pre-existing pattern); or one shared, authenticated endpoint that drains every registered job.

**Chose:** one endpoint, `POST /api/cron/run`, protected by a constant-time-compared `CRON_SECRET`, with each job (`notifications:drain`, `escrow:sweep-expired`, `offers:sweep-expired`, `escalations:expire`, `restock:scan`, `merchant-digests:send`, and L10's `webhooks:drain` if present) run in isolation so one throwing doesn't stop the rest.

**Because:** per-feature dashboard-load triggers is a demo answer that quietly assumes a merchant checks every page regularly — the whole point of Layer 11 is reaching a merchant who *doesn't*. A real production answer needs a real scheduler (Vercel Cron), and every feature that needs periodic work should register with the same one rather than each inventing its own. This also converged naturally with Layer 10's independent need for a webhook-delivery drain trigger, built on the same branch — see that layer's own "How the webhook runner is actually triggered" entry.

**Cost:** Vercel's free-tier cron runs at most once a day, so for a live demo the real driver is a manual `curl` or a short loop, not the deployed cron itself — documented rather than implied to be automatic. The existing opportunistic `/dashboard/escrow`-triggered sweep was kept as a supplement, not removed, so a merchant who does check the dashboard still gets an immediate sweep rather than waiting for the next cron tick.

### Tier honesty: real Groq models under their real names, never another vendor's name over a Groq response

**Context:** L11-8's initial framing asked for tiers labelled as if served by different vendors (Claude, GPT, Gemini) while actually all being served by the one configured Groq key.

**Options:** Label tiers with other vendors' model names regardless of which provider actually answered; or build the tiers from Groq's own real, differently-sized model lineup, honestly labelled.

**Chose:** the latter. Verified live against Groq's own `/models` endpoint (not guessed) which models this API key can actually call, then hardcoded three genuinely distinct ones as presets: `openai/gpt-oss-20b` (the app's existing default), `qwen/qwen3.8-27b` (a different model family), `openai/gpt-oss-120b` (a larger model in the same family). `ai_credit_redemptions.providerServed` records which provider actually answered on every single redemption, and a test (`ai-credits.test.ts`) asserts it matches the tier's own claim — the honesty property is enforced by code, not just asserted in a comment.

**Because:** relabelling a Groq response under another vendor's name is fabricated data — CLAUDE.md's design rule 14 ("decorative or fabricated data anywhere in the UI") and the project's broader no-mocks discipline both bar it outright, and it is the one claim on this surface a judge could trivially disprove by checking response characteristics or timing against the real vendor's API. The real product idea — tiered model access at different, merchant-set coin prices — is fully delivered by real tiering; nothing about the underlying mechanics (balance check, debit, refund-on-failure, audit trail) needed to be fabricated to make it work.

**Cost:** the tier lineup only spans what one Groq key can serve, which is narrower than a genuine multi-vendor console. A merchant wanting to visibly signal broader provider breadth would need a tier row marked "not connected — add a key" for an unconfigured provider (a real, checkable UI pattern many multi-provider consoles use) — considered, not built, since no second provider's key was in scope for this layer.

## Layer 12 — real OAuth, a real auth page, a sharper inner-app shell

### Hand-rolled OAuth2 instead of a library

**Context:** Google + GitHub sign-in needed to actually work (CLAUDE.md rule 14 bars interactive-looking elements that don't function), and this project has no auth library installed — sessions are already a hand-rolled DB-backed cookie (`src/lib/auth.ts`), not NextAuth/Clerk/Auth.js.

**Options:** add a library purpose-built for this (e.g. `arctic`, or the heavier NextAuth/Auth.js); or implement both providers' plain OAuth2 authorization-code flow directly.

**Chose:** hand-rolled, in `src/lib/oauth.ts` — `buildAuthorizeUrl()`, a code-for-token exchange, and a provider-specific profile fetch (Google's `userinfo` endpoint; GitHub's `/user` + `/user/emails`, since a verified primary email isn't reliably present on `/user` alone).

**Because:** CLAUDE.md's stated bar is "no new dependency without a clear reason it can't be done with what's installed." An OAuth2 authorization-code exchange is a small, standard, well-documented HTTP flow — two providers, one `fetch`-based token exchange, one profile fetch each. It genuinely doesn't need a library, and this codebase already owns its full session lifecycle (`createSession`/`destroySession`/the cookie itself), so a library would either have to be bent to write into that same session mechanism or the app would end up running two parallel session systems. Hand-rolling keeps one session system and a small, fully auditable surface.

**Cost:** no library maintainer keeping up with each provider's endpoint changes — if Google or GitHub changes their token/profile endpoint shape, this breaks and needs a manual fix rather than a dependency bump. Judged acceptable: both providers' OAuth2 endpoints are stable, standardized surfaces that rarely change shape.

### Auto-link by verified email, refuse on unverified

**Context:** A merchant who signed up with email/password and later clicks "Continue with Google" using the same address — should that sign into the existing account, or fail?

**Chose (confirmed with the user):** auto-link when the provider reports the email as verified and it matches an existing merchant; refuse (not silently create a second account, not silently attach) when the email is unverified.

**Because:** an unverified email is not proof of ownership — auto-linking on it would let anyone who controls an OAuth app claim any merchant's account by entering their email during signup without ever proving they own it. A verified flag from Google/GitHub is a real assertion the provider itself checked; refusing on unverified is the fail-closed answer CLAUDE.md's rule 4 already establishes for every other ambiguous-state decision in this codebase, applied here to identity resolution instead of money.

**Cost:** a merchant whose provider account has an unverified primary email (rare — both Google and GitHub verify by default) gets a generic "account already exists, log in with your password" message rather than being let in. Correct, not a real UX loss.

### Auth backdrop: a procedural CSS colour drift, not a video file

**Context:** The user's brief was specific — a background "similar" in spirit to payloadservice's own hero-video treatment, but a *new* clip with a very slow, continuous colour drift (indigo → brown) subtle enough that no single glance catches it moving.

**Options:** commission/generate a real video clip with a colour grade that shifts over its (necessarily short, looping) runtime; or build the drift procedurally, the same way `AmbientField` already replaces what would otherwise be a hero video on the landing page.

**Chose:** procedural — `AuthBackdrop` layers the existing `AmbientField` canvas under a new CSS-only layer (`.auth-backdrop-drift`), a 210-second `ease-in-out infinite alternate` keyframe cross-fading two radial washes (indigo, warm brown), under the existing dark scrim gradient for text legibility.

**Because:** a real video loop long enough to make a multi-minute drift read as "continuous" rather than "resets and jumps" would be a large asset for very little payback, and this project already has a firm precedent for exactly this substitution — `AmbientField`'s own docstring: "built procedurally instead of shipping a video file: zero binary weight, no licensing question, guaranteed-fast LCP." A CSS `@keyframes` animation can hit the requested duration and subtlety exactly, is trivially reduced-motion-safe (one frozen frame instead of extra work), and costs nothing to iterate on.

**Cost:** it's a mood wash, not literal footage — someone expecting an actual filmed background (matching payloadservice's literal implementation, not just its layering technique) would notice the difference on close inspection. Consistent with the product's own established visual language (the landing hero already made the identical tradeoff) rather than a new one-off.

## Layer 13 — Authorization, supervision, and proof

### AP2: a documented subset, not the full spec
**Context:** The Agent Payments Protocol (AP2) is the industry standard for merchant-verified mandates, but its full specification is the W3C Verifiable Credential / SD-JWT stack with selective disclosure — a much larger surface than this layer's timeline supports.
**Options:** Implement the full VC/SD-JWT stack; skip AP2 entirely and build an ad-hoc signed-token scheme; implement a clearly-scoped subset (Checkout Mandate + Payment Mandate verification, as plain ES256-signed JWTs) and say so plainly.
**Chose:** The subset.
**Because:** the spec's own most load-bearing requirement — mandate verification MUST happen in deterministic code — is exactly CLAUDE.md's rule 2, independently arrived at. Implementing that core honestly, and stating the scope precisely, is worth more than an overclaimed "full AP2" that quietly skips selective disclosure. A precise, working subset described accurately survives scrutiny; an overclaimed full implementation does not.
**Cost:** no selective disclosure (a Payment Mandate reveals its full claims to the merchant, not a minimal disclosed subset), and no interop claim with another AP2-conformant merchant's verifier — this codebase is both issuer and verifier of its own mandates, which is honest for a single-merchant-per-mandate flow but not a claim of cross-implementation interoperability.

### ECDSA P-256 (ES256), never Ed25519, for mandate signatures
**Context:** `jose` supports several signature algorithms; Ed25519 is faster and simpler to implement correctly.
**Options:** Ed25519 (EdDSA); ECDSA P-256 (ES256); RSA.
**Chose:** ES256.
**Because:** the AP2 spec explicitly forbids a deterministic signature scheme for this purpose. Ed25519's signatures are deterministic — the same message and key always produce the identical signature — which would let an attacker build a rainbow table mapping known `checkout_hash` values to their signatures, a real cryptographic weakness specific to signing a hash of a value with limited entropy (a cart total, a SKU list). ECDSA's signatures are non-deterministic (a fresh random nonce per signature), which structurally prevents this. This is a real, non-obvious constraint the spec states outright, not a stylistic preference — documented directly in `mandates.ts`.
**Cost:** ECDSA implementations are more failure-prone than Ed25519 if nonce generation is ever weak (the classic ECDSA nonce-reuse vulnerability) — mitigated entirely by using `jose`, a maintained, audited JOSE library, rather than hand-rolling ECDSA.

### The Runtime Guardian is a bound on the gate, not a parallel observer
**Context:** Supervision ("is this agent behaving normally right now") could be built as a dashboard-only monitoring feature that merely displays anomalies, or as something that actually changes what the gate allows.
**Options:** A read-only anomaly dashboard, decorative; a bound evaluated inline in `checkBounds()` that can deny a request outright.
**Chose:** A real bound — `evaluateAndTransition()` runs inside `checkBounds()`, and a suspended/revoked agent state denies before budget is ever reserved.
**Because:** a breaker that only observes and notifies demonstrates nothing on the money path itself — CLAUDE.md's bar is that a refusal is real, not that a dashboard is informative. Making the Guardian a bound (mirroring how the risk layer can only downgrade allow to escalate, never bypass a deterministic deny) means the same "the refusal is real" standard every other layer's failure demo proves applies here too, verified directly by `scripts/demo-failure-guardian-trip.ts`: a real retry-loop pattern suspends the agent, and the very next purchase attempt is denied with zero budget reserved.
**Cost:** the Guardian's SQL-computed signals now run on every money-action attempt (one cheap indexed query set), not just on a periodic sweep — a small latency cost on every purchase in exchange for the state actually mattering.

### Capabilities as an enum + join table, not a jsonb blob on `agents`
**Context:** `agents` needed a way to express which of several distinct actions an agent may take.
**Options:** A `jsonb` column of capability strings on `agents`; a `pgEnum` + a separate `agent_capabilities(agentId, capability)` join table with a unique index.
**Chose:** The enum + join table.
**Because:** a jsonb blob is unconstrained by the database — a typo'd capability string, or a value outside the intended set, would silently exist and silently never match any `requireCapability()` check, failing closed by accident rather than by design. The enum makes the valid set a schema-level fact (queryable, constrained, and — critically — refunds/payouts are structurally absent from it, so no code path can ever grant them, a stronger guarantee than "grant then remember to never call revoke"). A join table also makes "every agent holding capability X" a plain indexed query, useful for both the migration backfill and any future audit.
**Cost:** granting/revoking a capability is a small transaction (delete then insert the full set) rather than a single jsonb field write — negligible at this scale, and `setAgentCapabilities()` already wraps it in one `db.transaction`.

### Preflight shares `attemptMoneyAction` itself via a `dryRun` flag, not a second function
**Context:** A "what would happen" simulator needs to run every real check without executing anything — this can be built as a copy of the gate's logic with the execution step removed, or as the real gate function with an early-exit flag.
**Options:** A separate `simulatePurchase()` function that reimplements `checkBounds`'s logic; a `dryRun: boolean` field on `MoneyActionRequest` that `attemptMoneyAction` itself checks, short-circuiting right after `checkBounds` succeeds and before `reserveBudget`.
**Chose:** The `dryRun` flag on the real function.
**Because:** a parallel reimplementation of the rules is a lie waiting to happen — the two versions start identical and drift the first time either one is edited without the other, and nobody notices until a demo shows a simulation disagreeing with reality. Per the plan's own instruction: "a parallel reimplementation that simulates the rules would be a lie, and would drift from the real ones within a week." `gate.preflight.test.ts` proves the two paths (real vs. dry-run) hit the identical `checkBounds` failures for the identical inputs, because it is, literally, the same function call.
**Cost:** `MoneyActionRequest` grows one more optional field, and `attemptMoneyAction`'s body has one more early-return branch — a small increase in the gate's own surface area, in exchange for the honesty guarantee.

## Layer 14 — the AI Treasury and the economic loop

### The Treasury is explicitly a simulation of a product mechanism, not a claim about Razorpay's real economics
**Context:** Layer 14's central idea — a slice of GMV funds a pool for buyer/merchant AI spend — is genuinely original, but it is easy to imply it as a real statement about how Razorpay's own fees or settlement actually work, which this codebase has no basis to claim.
**Options:** Build it and let the mechanism speak for itself, letting a reader infer whatever they want about where the money "really" comes from; build it and state explicitly, in the UI and here, that the allocation rate is a merchant-set configuration parameter demonstrated with this project's own numbers, not a claim about real payment-processing economics.
**Chose:** State it explicitly, everywhere the mechanism appears.
**Because:** CLAUDE.md's rule 14 (no fabricated data) and this project's own broader "nothing renders that did not really happen" discipline extend naturally to a claim's *framing*, not just its numbers. A judge who reads "a slice of GMV funds this pool" without qualification will reasonably assume it means Razorpay's real transaction fee — which this project has no authority to state. Saying plainly that this is a configurable mechanism, merchant-set, demonstrated with real rows but a simulated rate, turns a potential credibility hole into evidence the team understands the difference between a product mechanism and a business claim (the plan's own framing).
**Cost:** none technically — every number the Treasury dashboard shows is still a real query over real `treasury_ledger` rows; the only change is one sentence of honest framing in the UI copy and this entry.

### A shared zod-defined rule AST over JSON Logic, for reward multipliers
**Context:** L14-3 needs a merchant (or an LLM drafting on the merchant's behalf) to express a conditional reward rule — "2x credits for returning customers above ₹500" — that gets evaluated deterministically, never executed as code.
**Options:** JSON Logic (an existing, widely-used library exposing ~40 generic operators over arbitrary JSON); a small, purpose-built zod schema exposing only the exact fields (`orderValuePaise`, `marginPercent`, `priorCaptureCount`) and comparisons (`gt`/`gte`/`lt`/`lte`/`eq`) a reward rule may legally touch.
**Chose:** The custom zod AST.
**Because:** JSON Logic's ~40 operators are almost entirely operators a reward rule has no legitimate reason to reach for (string concatenation, array manipulation, arbitrary variable substitution against an unconstrained data object) — accepting that surface from an LLM-drafted candidate widens the attack/mistake surface for no benefit this feature needs. It is also untyped at the codebase's own boundary: everywhere else user input crosses into deterministic code, it passes through a zod schema (agent requests, dashboard forms, mandate claims) — a JSON Logic rule would be the one place that discipline breaks. The custom AST is about 80 lines, adds no new dependency, gives end-to-end TypeScript types via `z.infer`, and validates at exactly the same boundary every other input in this codebase already crosses.
**Cost:** less expressive than JSON Logic — no OR conditions, no nesting, no arithmetic between two dynamic fields. Acceptable: the plan's own example ("above ₹500 AND margin exceeds 20%") needs nothing richer than a flat AND of comparisons, and a nested/OR form can be added later if a real merchant need for one shows up.

### Margin-derived reward multipliers stay inside `issueRewardCoinsForCapture`'s own call, never a second read path
**Context:** Computing a rule's `marginPercent` condition needs `productVariants.costPaise` — the single most sensitive column in the schema (CLAUDE.md's own comment: "never exposed on any agent-facing or public shape").
**Options:** Compute margin once inside the existing reward-issuance call and use it only to select a multiplier (an integer, itself carrying no information about the underlying cost or price); expose a general "evaluate this rule against arbitrary purchase data" utility that other, less-audited call sites might reach for later and accidentally pass cost data further than intended.
**Chose:** The narrow, single-call-site version — `buildRuleContext()` is called from exactly one place, and its `RuleContext` only ever leaves that function as a multiplier already applied to a coin count.
**Because:** the plan calls this layer "the highest-risk change yet" to `cost-paise-never-leaks.test.ts`'s guarantee, and the surest way to keep that guarantee is to minimize the number of places `costPaise` is ever read into memory at all, not to build a general-purpose API around it that a future feature might misuse. The new consolidated test in `cost-paise-never-leaks.test.ts` proves the margin figure derived from a real cost-marker product never reaches a reward balance, the Treasury overview, or a rule's own compiled description.
**Cost:** a merchant cannot yet build a rule keyed on margin outside the reward-issuance path (e.g., a merchant-facing "preview this rule against a hypothetical order" tool) without adding a second, equally careful call site — deliberately deferred rather than built speculatively.

### `periodStart` for a model budget comes from the database's clock, and is never reset by an edit
**Context:** `getUseCaseSpendPaise()` sums `model_call_costs` rows with `createdAt >= periodStart` to compute real spend — a real bug surfaced during this layer's own testing when `periodStart` was set from the app server's `new Date()` (see FAILURES.md).
**Options:** Keep `new Date()`, accepting the app/DB clock-skew risk; switch to `sql\`now()\`` (the database's own clock, matching `model_call_costs.createdAt`'s `defaultNow()`); additionally, reset `periodStart` to now on every budget edit vs. leaving it untouched after first creation.
**Chose:** `sql\`now()\`` on first creation, never touched again by `onConflictDoUpdate`'s `set` clause on a later edit.
**Because:** comparing a value from one clock (the app process) against a column stamped by a different clock (Postgres) is exactly the kind of subtle bug that makes an assertion like "budget is exhausted" quietly wrong without ever throwing an error — the arithmetic itself was correct, but the two inputs it compared didn't share an origin. Separately, resetting `periodStart` on every edit would mean a merchant adjusting their own budget mid-period erases real prior spend from the sum, letting a use case silently exceed what a merchant actually intended to allow it to spend in total.
**Cost:** none — this is strictly a correctness fix with no functional tradeoff; a genuine "start a new period" reset was never a requirement this layer's plan asked for, so it isn't built.

### OpenTelemetry without an external collector
**Context:** L15-1 needed distributed tracing (spans, tags, timing) without forcing merchants to run Datadog or Jaeger.

## Layer 16 — the multi-provider model router and inline model armor

### Three new providers via one OpenAI-compatible HTTP caller, not three new SDKs
**Context:** NVIDIA NIM, OpenRouter, and Z.ai all needed real, working integrations, and CLAUDE.md requires a clear reason before adding any new dependency.
**Options:** A dedicated SDK per provider (three new dependencies); one shared HTTP function serving all three, since each exposes the same OpenAI-compatible `/chat/completions` shape.
**Chose:** One shared `callOpenAiCompatible()` in `llm.ts`, parameterized by base URL, API key, and model id.
**Because:** all three providers' documented APIs are genuinely OpenAI-compatible at the endpoint level — verified live against each real endpoint, not assumed from documentation alone. A shared function is less code, less surface area to keep in sync with three vendors' SDK release cadences, and keeps every model call inside the one sanctioned wrapper CLAUDE.md already requires.
**Cost:** if a provider's response shape ever diverges from the OpenAI-compatible standard (a non-standard usage field, a different error shape), the shared function needs a provider-specific branch rather than the SDK handling it — an acceptable tradeoff since all three were verified against their real endpoints before being wired in.

### NVIDIA's model catalogue is priced (and routed to) one model at a time, not wholesale
**Context:** NVIDIA NIM's hosted catalogue has 80+ models reachable through one endpoint, but the layer's own no-fabricated-pricing discipline (`model-pricing.ts`) requires a real, cited per-token rate before a model is routable.
**Options:** Price and route the whole catalogue with an estimated or averaged rate; price and route only the specific model(s) with a real, sourced, verified rate.
**Chose:** One model, `nemotron-3-nano-30b-a3b`, verified live against the real endpoint with a real, cited $0.05/$0.20-per-1M-token rate.
**Because:** NVIDIA does not publish one token-price table for its whole hosted catalogue — its public pricing anchor is the NVIDIA AI Enterprise production license, not a commodity per-token bill. Inventing a blended or estimated rate for the rest of the catalogue would be exactly the kind of fabricated-data violation CLAUDE.md's design conventions call out. A first choice for this one model (`nemotron-nano-9b-v2`) was itself real and live when sourced, but returned a genuine HTTP 410 "reached its end of life" days later — the replacement was verified against the actual live endpoint before being committed, not re-sourced from search results alone (see FAILURES.md).
**Cost:** only one NVIDIA model is actually routable from this codebase today; the rest of the catalogue is reachable through the same endpoint but deliberately unpriced and unrouted rather than guessed at.

### OpenRouter's broker pricing is pinned as a dated snapshot, not treated as live
**Context:** OpenRouter re-sells models from many upstreams and its listed price for a given model can move as upstream pricing changes — different from Groq/Gemini's own directly-published rates.
**Options:** Treat every OpenRouter call as unmetered (never costed); pin a specific model id to its listed rate at the time this was written, with the same snapshot caveat every other row in `model-pricing.ts` already carries.
**Chose:** Pinned — `z-ai/glm-4.6` at $0.43/$1.75 per 1M tokens, OpenRouter's own listed rate at the time this was written, verified against the same rate Z.ai publishes directly for the identical model.
**Because:** `model-pricing.ts`'s entire pricing table is already explicitly documented as "a snapshot of published, publicly listed pricing at the time this layer was built, not a live-fetched rate" — OpenRouter's broker pricing doesn't need a fundamentally different treatment than Groq's or Gemini's, it just needs the same honesty applied to a source that happens to move a bit more often. Treating it as unmetered would understate real AI operating cost for any use case routed there, which the whole model-budget mechanism exists to track accurately.
**Cost:** if OpenRouter's real rate for this model drifts meaningfully from the pinned figure, the routing-savings and budget-consumption numbers this layer reports will be stale until the pricing table is refreshed — the same limitation every other row already carries, made explicit rather than new.

### Armor may block, armor may never approve — the same asymmetry as the risk layer, stated as this module's one governing rule
**Context:** A model-facing inspection layer is exactly the kind of component that can quietly grow the authority to approve something it shouldn't — a "looks safe" verdict from a scanner is one step from becoming a second gate.
**Options:** Let armor's verdict influence downstream permission (e.g., a clean verdict marks a call as pre-approved for something); restrict armor to a strictly one-directional check — it can refuse a call, and has no code path that grants anything.
**Chose:** Strictly one-directional. `inspectInbound`/`inspectOutbound` return a verdict with exactly two effects: proceed unchanged, or refuse and record why.
**Because:** this is the identical shape gate contract point 5 already established for `risk.ts` — "the risk layer can only downgrade, never approve past a deny" — for exactly the same reason: a component whose only job is caution should have no code path back toward permission. Stating it as the module's own docstring rule, not just an implicit property, keeps a future edit from accidentally wiring a "clean" verdict into anything that grants access.
**Cost:** none functionally — this is a pure constraint on the design space, not a capability given up.

### Armor's audit excerpt is scrubbed against the same PII patterns, then any remaining 4+ digit run is redacted outright
**Context:** `cost-paise-never-leaks.test.ts`'s own Layer 16 extension caught a real leak: a bounded-by-length excerpt around a matched injection rule could still contain a sensitive number sitting in that window (see FAILURES.md) — "bounded by length" and "safe to log" turned out not to be the same property.
**Options:** Bound the excerpt by length only (the first implementation, proven insufficient); scrub the excerpt against the same PII shapes `inspectOutbound` already checks; additionally redact any bare run of digits, broader than PII shapes alone.
**Chose:** Both — PII-pattern scrubbing first, then a blanket 4+-digit redaction.
**Because:** the actual threat here isn't "does this excerpt look like a phone number," it's "does this excerpt carry any number that could matter" — a cost figure, an account fragment, an amount. A payload deliberately crafted to be logged is itself an attack (this module's own docstring already said so before the leak was found), and the fix has to match that threat model rather than a narrower one.
**Cost:** a legitimate number relevant to understanding why a rule fired (e.g., a quantity mentioned in the blocked message) is also redacted from the excerpt — an acceptable tradeoff since the excerpt's job is proving a rule fired and roughly why, not preserving every detail of a message that was refused specifically because it shouldn't be trusted.

### `risk.ts` stays on Groq, with no provider preference, even though Layer 16 widened what's routable
**Context:** `model-router.ts`'s new `preferredProvider` could in principle be set for any use case, including ones adjacent to a money decision.
**Options:** Extend provider routing to `risk.ts`'s model call; leave it deliberately unrouted, staying on Groq.
**Chose:** Left on Groq, unrouted.
**Because:** `risk.ts` is the one model call this codebase runs adjacent to a real money decision, and its `deterministicFallback()` prefix is a real, load-bearing contract — `explainability.ts` reads that exact prefix to correctly label a risk-influenced decision `deterministic` rather than `model_influenced` when the model was unavailable. Groq is also the only provider this project has real operating history for under this workload (including its own documented per-day token quota exhaustion under heavy testing). Routing this one call to an unproven provider would trade a known, tested failure mode for an unknown one, on the one call path where getting that wrong is most consequential.
**Cost:** `risk.ts` doesn't benefit from any cost or capability advantage a different provider might offer — deliberately, since this is the one call in the app where "proven" outweighs "cheaper" or "more capable."

## Layer 17 — the Agent Runtime

### A Postgres table plus an atomic conditional UPDATE, not Temporal/BullMQ/Kafka/an external queue
**Context:** long-running task execution needs somewhere durable for a task's state to live across ticks, since this stack has no worker process to hold it in memory.
**Options:** Adopt an external workflow engine or queue (Temporal, BullMQ, Kafka); build the state machine directly on Postgres, reusing the gate's own proven atomic-claim pattern.
**Chose:** Postgres — `agent_tasks`/`agent_task_steps`, claimed via the identical conditional-`UPDATE`-with-the-check-in-the-`WHERE` pattern `gate.ts`'s `reserveBudget`/`reserveStock` already use.
**Because:** Layer 13 already rejected Temporal and Kafka on the grounds that they replace working, tested code with infrastructure risk — that reasoning is the direct precedent here, not a new argument. A conditional `UPDATE` with the eligibility check in its own `WHERE` clause is a real, durable, transactional queue, and it is the one primitive this codebase already knows how to prove correct under concurrency (gate contract point 1's own "20 concurrent requests, exactly 5 allowed" standard). Adding a new infrastructure dependency for a problem this project's own database already solves would be exactly the kind of complexity CLAUDE.md's "no new dependency without a clear reason" rule exists to prevent.
**Cost:** no built-in workflow visualization, no distributed cron across multiple app instances beyond what Postgres row-locking already provides, and polling (via `/api/cron/run`'s tick) rather than push-based wakeup — all acceptable for a single-process demo-to-production-scale product, and each is exactly what an external queue would have bought at the cost of a new dependency and a new failure mode.

### No worker process — a durable state machine advanced by the existing cron tick, not a sleeping thread
**Context:** the runtime needs to carry out multi-step, time-spanning work (a recovery sequence's real backoff windows), and this stack (Next.js on serverless functions) has nowhere to run a long-lived background process.
**Options:** Pretend a worker process exists and design around it, accepting that the design won't survive a real deployment; design the runtime honestly around what this stack can actually do — a state machine whose every transition is a row, advanced only when something external (the cron tick) invokes it.
**Chose:** The honest design — no task ever "runs" in the sense of holding a thread; it is claimed, one step is carried out, and it either terminates or returns to being a waiting row until the next tick claims it again.
**Because:** a fictional worker process would produce code that looks right in isolation and breaks the moment it meets a real deployment — exactly the trap CLAUDE.md's "targets real merchant use, not just a judged demo" framing warns against. The tick-advanced design is also strictly more auditable: every state transition is a row with a timestamp, not a stack frame that vanishes if the process restarts.
**Cost:** a task's `runAfter` is honored on the *next* tick, not at the instant it becomes due — true responsiveness depends on how often the external scheduler actually fires (see ARCHITECTURE.md's "What's deliberately not here yet"). Acceptable because the state machine's correctness never depends on tick frequency, only its felt latency does, and every real backoff window in this codebase is minutes-to-days, not seconds.

### `claimDueTasks`'s eligibility check treats an expired lease as equivalent to "never claimed," found by this layer's own property-based test before it shipped
**Context:** the first implementation's eligibility check was `status IN ('pending', 'waiting')` — plausible-looking, and it passed every example-based happy-path test.
**Options:** Ship the status-only check, accepting that a crashed process's task would never be reclaimed; add a second eligibility path for "claimed, but the lease has expired," treated as equivalent to unclaimed.
**Chose:** The second — one shared `taskEligibilityCondition()` used identically by the read and the claiming update, so the two can never drift apart.
**Because:** a real crash-simulation test (claim a task, then force its lease into the past exactly as a real crash would leave it) found the gap directly: the lease's own expiry did nothing, because the status gate that comes first in the `WHERE` clause never reopened once a task moved to `claimed`. This is precisely the property the plan calls "the single most important correctness property in the layer," and it took an adversarial test — not a happy-path one — to surface it. See FAILURES.md.
**Cost:** none — this is a correctness fix with no functional tradeoff; the plan always required this property, the first implementation simply hadn't achieved it yet.

### `rescheduleTask` is guarded by `WHERE status = 'claimed'`, closing a real terminal-task-resurrection bug the same property test caught
**Context:** the first implementation of `rescheduleTask` was an unconditional `UPDATE ... WHERE id = ?`, unlike every other mutation in the module.
**Options:** Leave it unconditional, trusting every caller to only ever call it on a genuinely claimed task; add the same `WHERE status = 'claimed'` discipline every other function in the module already has.
**Chose:** Guarded.
**Because:** the DB-backed property test generated a sequence that called `rescheduleTask` on an already-`succeeded` task and found it silently flipped back to `waiting` — a direct violation of "a terminal task never transitions again," one of this layer's own definition-of-done requirements. An unconditional mutation trusting caller discipline is exactly the shape of bug that survives until a sequence nobody thought to write by hand exercises it; the property test's randomly generated sequences did.
**Cost:** none — this closes a real bug with no loss of legitimate functionality; no real caller in this codebase ever needed to reschedule a terminal task.

### `terminateTask`'s shared UPDATE excludes every terminal status, closing the identical class of bug one function away from the one just fixed
**Context:** `completeTask` and `abandonTask` both call one shared `terminateTask()` helper, and — discovered by the same property test on a later run, after `rescheduleTask`'s own guard was already in place — that helper had no terminal-status exclusion at all, so calling `abandonTask` on an already-`succeeded` task silently overwrote it to `failed` and wrote a second, contradictory audit entry.
**Options:** Fix `abandonTask`/`completeTask` individually with their own ad hoc checks; fix the shared `terminateTask` helper underneath both, once.
**Chose:** The shared helper — its own `UPDATE`'s `WHERE` clause now excludes `succeeded`/`failed`/`cancelled` outright, and the audit write is skipped whenever the update affects zero rows.
**Because:** the bug lived in the one function three callers shared, so fixing it there closes it for all three at once rather than trusting each call site to remember the same discipline independently — the same reasoning `taskEligibilityCondition()` already applies to `claimDueTasks`' SELECT and UPDATE. `cancelTask` had happened to be safe only by accident (its own separate pre-check-and-throw ran before ever reaching `terminateTask`), which is exactly the kind of coincidence that stops holding the moment someone adds a fourth caller.
**Cost:** none — a genuine correctness fix with no loss of functionality; every real caller of `completeTask`/`abandonTask`/`cancelTask` only ever calls them on a task that should still be transitionable.

### `attemptCount` increments at the moment of claiming, not at reschedule — one place, not two
**Context:** the first implementation incremented `attemptCount` inside `rescheduleTask` (via an `incrementAttempt` flag), which meant a task orphaned by a crash — one that gets reclaimed via the expired-lease path rather than an explicit reschedule — would never have its attempt counted at all.
**Options:** Keep incrementing at reschedule time, accepting that a crash-and-reclaim cycle undercounts attempts; move the increment to `claimDueTasks` itself, the actual instant an attempt begins regardless of how it ends.
**Chose:** Increment at claim time; `rescheduleTask` no longer touches `attemptCount` at all.
**Because:** an attempt "begins" the moment a task is claimed, not the moment it's rescheduled after failing — and a real crash between those two moments is exactly the case the lease mechanism exists to handle. Counting only at reschedule time would let a task that crashes on every attempt (rather than failing cleanly and rescheduling itself) retry forever, since it would never reach the code path that increments the counter — the opposite of the retry ceiling's whole purpose.
**Cost:** none — this is strictly a correctness fix; the observable retry ceiling behavior for a normally-completing attempt is unchanged, only the crash case is now counted correctly.

## Layer 18 — the Memory Bank

### Memory is context, never a bound — the gate has no wire to it at all
**Context:** the whole layer exists to give the assistant real, persistent context about a returning buyer. The obvious next step for a system with memory is to let it inform a decision — a "known good customer" discount, a raised limit for someone with a long purchase history, a lighter Guardian threshold for a trusted agent.
**Options:** Let a derived fact (e.g. prior purchase count) feed into risk scoring or a spend cap as a modifier; keep memory strictly read-only with respect to every money decision, with no code path from `agent_memories` into `gate.ts`, `risk.ts`, or `guardian.ts` at all.
**Chose:** Strictly read-only. Not one field of a memory row is ever read by anything that decides a spend cap, a stock check, a price, a margin, a retry count, an escalation threshold, or a Guardian signal.
**Because:** this is CLAUDE.md rule 2 ("AI decides judgment, code decides limits") at its sharpest edge, because memory is exactly the shape of thing that eats that boundary quietly — a "remembered" trust level or a "they always pay" allowance is a bound decided by accumulated impression rather than by code, and it would arrive looking like a reasonable product feature rather than a violation. The proof this holds is deliberately two-layered: a cheap static check that `gate.ts`'s own source names no `@/lib/memory` import, and the real proof — a behavioural test (`memory-never-influences-gate.test.ts`) and a standalone demo (`demo-memory-does-not-move-the-gate.ts`) that run the identical purchase through the real gate with and without a rich, deliberately adversarial memory bank planted for the same agent, and assert the decision and reason are byte-identical.
**Cost:** a genuinely useful signal ("this buyer has never had a failed payment") is left on the table as a risk input, even though it might be a legitimate improvement to `risk.ts`'s judgment in a system with a different threat model. Acceptable because the alternative — any wire at all from a store of remembered, partly buyer-influenced facts into a money decision — is a structural risk this product is not willing to take on for the value of one extra risk signal.

### Two kinds of memory only, derived and stated — no inferred/opinion kind
**Context:** the natural next kind of memory beyond "a real fact about a real event" and "something the buyer explicitly said" is an inference — "seems price-sensitive," "likely to churn," a computed trust score. These are exactly the features a recommendation or CRM system usually builds next.
**Options:** Add a third kind (`inferred`) computed by a model or a heuristic from behavioural signals; hold the line at two kinds — `derived` (a deterministic query over a table this codebase already owns) and `stated` (something the buyer or merchant explicitly said).
**Chose:** Two kinds only.
**Because:** an inferred/opinion memory is not a record of anything that actually happened — it's a model's guess stored as if it were a fact, and CLAUDE.md's no-fabricated-data discipline (already enforced everywhere else in this product, from `EmptyState`'s no-fake-rows rule to the offer engine's floor-first filtering) applies here just as much. It is also one small step from becoming exactly the bound the "memory is never a bound" rule above forbids — a "seems price-sensitive" tag is an obvious candidate for a future developer to wire into a discount decision, and the two-kind design makes that mistake harder to make by construction, since there is no field that could hold such a judgment in the first place.
**Cost:** the assistant cannot express a genuinely useful soft signal like "this customer tends to negotiate hard" even where it might improve the conversation. Acceptable — the risk of normalising stored opinions about people outweighs that conversational polish.

### Subject anchors are `customer_contact` and `agent` only — an anonymous storefront visitor gets no memory
**Context:** most of this product's real chat traffic is anonymous — a `conversations.sessionToken` with no email or account behind it, since the storefront is deliberately session-based with no buyer login (ARCHITECTURE.md's "what's deliberately not here yet").
**Options:** Invent a fingerprint (IP, user-agent, a persistent cookie) to recognise a returning anonymous visitor across sessions; anchor memory only to identities this product genuinely has durable, consented records for, and accept that a visitor with no `customer_contact` and no agent identity gets no memory at all.
**Chose:** Real anchors only — `customer_contacts` (an email, consented and already governed by Layer 11's unsubscribe/consent-provenance discipline) and an authenticated agent id. No fingerprinting.
**Because:** a device or IP fingerprint is both a privacy problem (tracking someone who never gave a real identity) and, more simply, a fabrication — it would let the product claim to "remember" someone it cannot actually re-identify with any honesty, the same category of dishonesty CLAUDE.md's no-fabricated-data rule already rules out for a sample row or a placeholder metric. "No memory for this subject" is treated as a normal, common, honestly-rendered state — the identical posture the recovery pipeline already takes toward "no customer contact is on file."
**Cost:** the majority of real storefront chat sessions today are genuinely unrecognisable across visits, so most of the product's actual traffic sees no memory benefit yet. This is a real, stated limit, not an oversight — it directly motivated wiring `chat.ts`'s `provide_contact` branch (previously a fire-and-forget restock-alert email capture) to persist a real `customerContactId` onto the conversation, which is what makes any memory reachable through the chat surface at all.

### A closed key vocabulary, not free-form text, as the structural injection defence
**Context:** a stated memory originates from an untrusted party (a buyer's own words) and is later replayed into a system prompt on a future, unrelated session — the single most dangerous shape of prompt injection this product has, because it survives past the session it was planted in.
**Options:** Store the buyer's statement as free text and rely entirely on Model Armor's pattern-based scan at extraction time to catch anything dangerous; constrain both the memory's `key` (a small, closed enum) and its rendering (one fixed template per key) so a stored value is never concatenated raw into a prompt, regardless of what content made it past validation.
**Chose:** The closed vocabulary plus fixed templates, with Model Armor's `inspectInbound` as a second, additional layer at extraction time — not a replacement for it.
**Because:** a pattern-based scanner is inherently a blocklist, and blocklists miss novel phrasings; the closed vocabulary is a structural defence that holds even against a payload the scanner has never seen, because the attacker only ever controls the *value* slot inside a template the system chose, never the sentence structure or position within the prompt. This mirrors `reward-rules.ts`'s own precedent exactly (a zod grammar closed to a small comparison-and-field vocabulary, not an arbitrary expression), applied here to protect a prompt rather than an arithmetic evaluator.
**Cost:** the assistant can only remember the handful of things this codebase has explicitly built a key and template for (a dietary restriction, a stated preference, a size preference) — a buyer stating something outside that vocabulary is simply never captured as a stated memory. Acceptable, and revisit by adding a new key deliberately (a schema change, not a runtime one) if a real merchant need shows up.

### Confirmation is required for every stated memory; nothing auto-confirms
**Context:** extraction is a real, non-deterministic model call, and a misread or over-eager extraction ("I hate the espresso blend" read from sarcasm, or a customer's throwaway remark) becoming a permanent, retrieved fact about a real person is a genuine harm, not just an annoyance.
**Options:** Auto-confirm any candidate that passes zod validation, on the theory that validation is enough of a gate; require an explicit human confirmation step before a stated memory is ever retrievable, exactly mirroring `reward-rules.ts`'s draft-then-approve precedent for an LLM-drafted rule.
**Chose:** Explicit confirmation only — a merchant action on `/dashboard/memory`, proven by `writeStatedMemory` always inserting with `confirmedAt: null` and `getMemoryFactsForSubject` filtering strictly on `confirmedAt IS NOT NULL`.
**Because:** validation only proves a candidate is *well-formed* (a legal key, a value within length bounds) — it says nothing about whether the model correctly understood what the buyer meant. The same reasoning that makes an LLM-drafted reward rule inert until the merchant reviews its compiled English description applies with more force here, since a reward rule is reviewable and reversible on the merchant's own terms, while a wrong "fact" about a customer, once retrieved and acted on in conversation, is a real reputational and trust cost the moment it's said aloud.
**Cost:** a genuinely correct extraction sits unused until a merchant visits `/dashboard/memory` and confirms it — there is currently no notification nudging them to do so beyond the sidebar's pending-count badge. Acceptable for this layer's scope; a merchant-facing notification for pending memories is a small, separable follow-on (Layer 11's notification queue already exists to carry it) rather than a reason to weaken the confirmation requirement itself.

### Update-in-place, not an append-only history table, for a memory's value
**Context:** several other durable ledgers in this codebase (`reward_coin_ledger`, `treasury_ledger`, `guardian_transitions`, `agent_task_steps`) are deliberately append-only, so a live balance or state is always a computed `SUM`/latest-row read, never a mutable column that can drift from the evidence behind it.
**Options:** Make `agent_memories` append-only too, keeping every prior value and deriving "the current fact" as the latest row per key; use one row per `(merchantId, subjectType, subjectId, key)`, updated in place on a correction, enforced by the schema's own unique index.
**Chose:** Update-in-place, via `onConflictDoUpdate` in both `derived.ts` and `stated.ts`.
**Because:** the append-only precedent exists specifically for things that are sums or sequences of independent events — a coin balance is the sum of every issuance and redemption, a task's history is a sequence of real attempted steps. A memory fact is neither: "this customer's dietary restriction" is a single current answer, not a quantity that accumulates, and retrieval (per L18-4) is explicitly required to never surface two conflicting answers for the same key. An append-only table here would just move the "which row is current" ambiguity into every reader instead of resolving it once at the schema level via the unique index.
**Cost:** a stated memory's correction history is not preserved anywhere — once a value is corrected, the prior value is gone, with only the row's `updatedAt` timestamp as evidence a change happened. Acceptable given the layer's own explicit L18-5 requirement ("correction over accumulation... it does not sit alongside the old one where retrieval might surface both"); if a future need for correction history emerges, add it as a genuinely separate audit trail rather than repurposing the live table's own shape.

### The honest limit of buyer-facing deletion: no buyer accounts means no buyer self-serve UI
**Context:** memory stores information about real people, and a mechanism to be forgotten matters from the start, not as a retrofit — but this product's storefront is deliberately session-based with no buyer login (a standing product decision this layer does not reverse).
**Options:** Build a buyer-facing "forget me" page gated by the same unsubscribe-token pattern Layer 11 already uses for email opt-out; ship only a merchant-facing delete action on `/dashboard/memory`, and state plainly that a buyer's path to deletion today is asking the merchant, who can act on that request in one click.
**Chose:** Merchant-facing deletion only, real and audited (`memory_deleted`), plus expiry (`expiresAt`, swept by `/api/cron/run`) as the second, non-request-driven retention mechanism.
**Because:** inventing a buyer-facing deletion flow would require inventing some form of buyer identity verification this product doesn't have — reusing the unsubscribe-token pattern is tempting but that token authenticates "stop emailing this address," not "you are this address's owner, entitled to see and erase what's stored about you," and conflating the two would be a real, if well-intentioned, security shortcut. Naming the honest limit here (a merchant acting on a buyer's request is a real, if manual, answer — the same posture the recovery pipeline already takes toward "no customer contact is on file") is more truthful than quietly shipping a thinner buyer-facing flow with weaker guarantees than it appears to have.
**Cost:** a buyer who wants a memory deleted must ask the merchant directly (email, chat, however they'd normally reach out) rather than clicking a link — a real, stated gap. Revisit only alongside buyer accounts, which is out of scope for this layer by design (see plans/layer-18-memory-bank.md's "deliberately not built").

## Layer 19 — The Adversarial Buyer and the Theatre

### `@google/adk`, Google's own TypeScript ADK package, over `@google/genai` alone or the unofficial `@iqai/adk`
**Context:** the plan asked for "a Google Agent Framework — ADK preferred if its TypeScript surface is workable; GenAI SDK is the acceptable fallback — decide by reading the actual installed package, not from memory."
**Options:** `@google/genai` alone (the plain SDK the parent app's `risk.ts` already imports for a different purpose — not one of the four named frameworks); the unofficial `@iqai/adk` community port (pre-1.0, not Google's own publishing account); `@google/adk` (npm-published by `google-wombot`, Google's own account, mirroring the official `google/adk-js` repo, v2.0.0 at the time of building).
**Chose:** `@google/adk`, installed and its real type declarations read directly (`LlmAgent`, `Runner`/`InMemorySessionService`, `MCPToolset`/`MCPSessionManager` under the `@google/adk/tools/mcp` subpath) before any code was written against it, per the plan's own "not from memory" instruction.
**Because:** it is genuinely Google's first-party ADK surface for TypeScript — not the unofficial community package, not a workaround — and it ships a built-in `MCPToolset` that speaks Streamable HTTP against a real MCP server out of the box, which is exactly this layer's transport. `@google/genai` alone would have meant hand-rolling the tool-calling loop and the MCP client from scratch; `@iqai/adk`'s unofficial, sub-1.0 status made it the weaker choice against an ADK that turned out to be directly usable.
**Cost:** a heavier dependency tree than a minimal `@google/genai`-only client would need (Vertex AI client, OpenTelemetry stack, `mikro-orm` for session persistence this layer doesn't use, `google-auth-library`) — acceptable since `agent-buyer/` is a standalone package outside the main app's own build, so none of this weight reaches the merchant platform's bundle.

### The injection scenario travels through `/api/agent/purchase`'s v1 `context` field, not `negotiate`
**Context:** the plan named "a negotiation message" as the honest free-text field for the injection scenario — "do not invent a new input surface to have something to block." Reading the real code first (rather than building around the plan's wording) found that `negotiate`'s MCP schema has no free-text buyer field at all (only a numeric `offerUnitPricePaise`), and Model Armor's `inspectInbound` was wired only into `chat.ts`'s human-facing storefront path — never into any agent-Bearer-authenticated route.
**Options:** Add a new optional buyer-message field to `negotiate`'s schema and wire armor into `negotiation.ts` (closer to the plan's literal wording, but a genuinely new field on an existing tool's contract, and `negotiation.ts`'s LLM call today never sees buyer-supplied text at all — only a number); skip the injection scenario for this layer, noting the gap; wire Model Armor into `/api/agent/purchase`'s existing v1 `amountPaise`+`context` shape, which already accepts real agent-authored free text and already flows into `money_actions`/the audit trail, just was never armor-inspected.
**Chose:** The third option — asked the user directly given the real discrepancy between the plan's wording and the actual surfaces, and this was the answer: complete Model Armor's coverage of a field that already exists, rather than invent a new one or leave a named scenario out.
**Because:** the field, its schema, its route, and its audit-trail write were all real and pre-existing — the only new code is the `inspectInbound()` call itself, on the exact branch (`variantId` absent) where the context sentence is genuinely agent-authored rather than server-generated. This is structurally identical to what `chat.ts` already does for the human-facing path, just extended to the one agent-facing surface that had the same real gap. `mcp-server.ts`'s `purchase` tool builds its own `context` string server-side in every branch, so there was never a comparable agent-controlled free-text field reachable over MCP itself — the REST v1 path is the only genuine candidate in the whole product.
**Cost:** the injection scenario is demonstrated over the REST `/api/agent/purchase` route, not the MCP `purchase` tool `agent-buyer/` primarily uses — a real, honest gap, noted rather than hidden. If a genuine buyer-controlled free-text field is ever added to an MCP tool (a real product need, not manufactured for this demo), armor coverage should extend there too.

### The buyer agent's own loop is multi-turn with an explicit continue-prompt, not ADK's single-shot `runEphemeral`
**Context:** ADK's `InMemoryRunner.runEphemeral()` is the documented quick-start shape — one call, one response. Using it directly against a real multi-step goal (check budget, search, negotiate three times, purchase) stopped after the model's first turn produced text instead of a further tool call, even mid-negotiation, because a single `runEphemeral` call only drives one agent turn to its natural end.
**Options:** Keep `runEphemeral` and accept that a run only ever completes a single turn's worth of tool calls (observed live: the agent stopped after opening a negotiation, having done nothing wrong — the mechanism just never asked it to continue); build an explicit outer loop using `Runner.runAsync()` with a persistent `InMemorySessionService` session, re-prompting "continue working toward the goal" after every turn that made at least one tool call, until a turn makes none.
**Chose:** The explicit outer loop.
**Because:** the plan's whole thesis needs a run that can be "refused several times, adapts, and then completes a real purchase" — genuinely impossible if the harness only ever drives one agent turn. The stopping condition (a turn with zero tool calls) is a real, checkable signal of the model's own claim of completion, not an arbitrary loop count; `bounds.ts`'s deterministic ceilings (`maxSteps`, `maxRunMillis`, `maxPurchaseAttempts`) still bound the whole multi-turn loop independently, so this isn't trading a bounded mechanism for an unbounded one.
**Cost:** more real HTTP/model-call volume per run than a single-shot call, and a second failure mode to handle honestly — a turn that produces neither a tool call nor any text (observed live, from an ADK event carrying only `errorCode`/`errorMessage`) must be a real, distinguishable error, not silently treated as "the model is done" (see FAILURES.md).

### Theatre correlation by real money action id, verified against `money_actions`, never by timestamp
**Context:** the buyer agent's run log and the merchant's decision stream are two independent, differently-timed data sources — a step and a decision that happen "around the same time" is exactly the kind of plausible-looking pairing CLAUDE.md's no-fabricated-data rule forbids, and the plan named this explicitly as the wrong approach.
**Options:** Pair a buyer step to a decision by nearest timestamp (simple, but a fabrication — two unrelated events can land within the same second, and a slow model call can make a genuinely correlated pair look temporally distant); pair by the real money action id the product already returns to the caller on every gated call, with the theatre view independently re-verifying that claimed id against a real `money_actions` row scoped to the viewing merchant before ever treating it as real.
**Chose:** Real id, independently re-verified at read time (`dashboard.ts`'s `verifyMoneyActionIds()`), never trusted from the untrusted blob alone.
**Because:** the id is already a real, existing part of the contract — `/api/agent/purchase` and the MCP `purchase`/`redeem_reward_coins` tools already return `moneyActionId` in their result, and `/api/agent/actions/[id]` already exists precisely so an agent can look up its own outcome by that id. Re-verifying it server-side (rather than trusting whatever the untrusted run-log blob claims) is what makes the pairing honest even though the blob itself is opaque, untrusted, agent-authored content — the same "the buyer's log is inspected, not executed" discipline the ingest route and `dashboard.ts`'s parser both apply.
**Cost:** a step whose tool call took no money action (every read tool, a refused negotiation turn) simply has no pairing on the right — shown as such, never invented. A run that never completes a real purchase produces a theatre view with zero correlated rows, which is the honest result for that run, not a bug to paper over.

### The failure demo drives a real in-process MCP client/server pair, not `attemptMoneyAction()` directly, and makes no live Gemini call
**Context:** the plan asked for a failure demo "distinct from `demo-failure-cap-exceeded.ts` in that the caller is the real autonomous agent making its own decision to try, rather than a script asserting a known-bad amount" — but a live Gemini call inside an unattended demo script risks exactly the daily/per-minute quota exhaustion this layer's own live testing hit repeatedly (see FAILURES.md), which would make the demo unreliable to run for a judge on request.
**Options:** Drive the real `agent-buyer/` package end to end with a live Gemini call inside the demo script (closest to "the real autonomous agent," but inherits the free tier's real quota fragility); call `attemptMoneyAction()` directly, identical in shape to `demo-failure-cap-exceeded.ts` (reliable, but not meaningfully distinct as the plan asked); drive a real MCP `Client`/`McpServer` pair over `@modelcontextprotocol/sdk`'s `InMemoryTransport` — the exact protocol surface, tool schema, and Bearer auth `agent-buyer/`'s own MCP client uses against the real `/api/mcp` route — with the specific hostile call (an over-cap quantity) hardcoded rather than modeled by a live agent.
**Chose:** The third option.
**Because:** it proves the bound holds for a caller shaped like a real autonomous agent's tool call — the real MCP protocol round trip, the real tool schema and response parsing, the real `createMcpServerForAgent()` — without depending on a live model's own decision to attempt it, which live testing already proved is exactly what a real, unscripted `agent-buyer/` run does (reproduced verbatim in FAILURES.md as the actual demonstration of that behaviour). This mirrors `demo-failure-upsell-refused.ts`'s own precedent for the same reliability reasoning (Layer 6, avoiding Groq's daily-quota flakiness in that layer's own required demo).
**Cost:** this specific script's refusal is deterministic (a hardcoded over-cap quantity), not the model's own emergent decision to try it — the honest, separately-documented answer to "did the model itself really try to overspend" is the live run in FAILURES.md, not this script. Two different pieces of evidence for two different claims, not one script overclaiming both.

## Layer 23 — Deployment and the agent-pressure surfaces

### Cloud Scheduler over Cloud Run for the Google Cloud requirement, at this point in the build order
**Context:** the Google submission needs at least one real Google Cloud infrastructure service with visible proof. The plan's own ranked options were Cloud Run hosting the app, Cloud Run hosting the Layer 19 buyer agent, Cloud SQL, or Cloud Scheduler driving `/api/cron/run`. The build order puts Layer 23 before Layer 19, so the buyer agent — Cloud Run's most natural, most honest target — doesn't exist yet.
**Options:** Build a throwaway Cloud Run service now just to have one (a container with no real long-running purpose yet); migrate to Cloud SQL this late in the build; wait and do the whole of L23-1 after Layer 19 lands so Cloud Run has something real to host; ship Cloud Scheduler now (a real, already-documented gap) and add Cloud Run once Layer 19 exists.
**Chose:** Cloud Scheduler now, driving the existing `POST /api/cron/run` at a 1-minute cadence. Cloud Run deferred to immediately after Layer 19, documented as a follow-on in DEPLOYMENT.md rather than silently dropped.
**Because:** a throwaway Cloud Run container built only to satisfy a judge's checklist is exactly the "compliance costume" the plan explicitly warns against — real infrastructure solving a real problem was the bar, and Cloud Scheduler clears it on its own: ARCHITECTURE.md already documented, across two separate layers (11 and 17), that the Agent Runtime and the webhook outbox both need a real external scheduler in production and that Vercel's free-tier cron (at most daily) can't be it. Waiting for Layer 19 to do L23-1 in one pass would have meant deploying nothing until much later in the build — the plan itself names deployment as "the single highest-leverage item... most likely to be left until it is too late," which argues for shipping the real, available half now rather than blocking on the half that isn't ready yet.
**Cost:** the submission's Google Cloud proof is Cloud Scheduler alone until Layer 19 lands and Cloud Run is added — a real, working service, but a smaller one than the two-service story the plan sketched. If Layer 19 doesn't ship before submission, this is the final state, and it should be described honestly as such rather than implied to be more than it is.

### The Cloud Scheduler cadence is 1 minute, derived from the tightest deterministic deadline the codebase now has, not chosen loosely
**Context:** a scheduler cadence is a real, checkable number — it directly determines how long a swept condition (an abandoned reservation, an expired escalation, a due task) sits before the next tick catches it.
**Options:** Every 5 minutes (round, easy to remember); every 15 minutes (matches the Guardian's own `RECENT_WINDOW_MINUTES`); every 1 minute (Cloud Scheduler's minimum granularity).
**Chose:** 1 minute.
**Because:** Layer 23-2 introduced `RESERVATION_TIMEOUT_MINUTES = 5` as the tightest real deadline anything in this codebase now sweeps against. A 5-minute tick would mean a reservation could sit stranded for up to 10 minutes in the worst case (expires just after a tick, caught by the next one 5 minutes later) — visibly looser than the bound itself implies. A 1-minute tick keeps real-world lag on every sweep (this one and every prior one — escrow, escalations, Guardian, the task runtime) comfortably inside its own stated deadline rather than merely approximating it.
**Cost:** more scheduler invocations (still well within Cloud Scheduler's free tier — one job ticking every minute is nowhere near the free-tier job-count limit that actually matters, since cost there is per-job, not per-invocation) and marginally more database load from more frequent no-op sweep queries when nothing is due. Acceptable; every sweep query here is a cheap, indexed, mostly-empty-result read.

### `money_actions.reservationExpiresAt` as a column on the existing table, not a new `stock_reservations` table
**Context:** the plan named `escrow_holds` (a separate table with its own `expiresAt`) as the pattern to follow. A genuinely separate `stock_reservations` table, one row per reservation, was the more literal reading of that pattern.
**Options:** A new `stock_reservations` table (moneyActionId, variantId/offerId/cartId, expiresAt, status) mirroring `escrow_holds`'s shape exactly; a nullable `reservationExpiresAt` column directly on `money_actions`, set only while `status = "allowed"`.
**Chose:** the column.
**Because:** unlike an escrow hold — which is a genuinely separate concept layered on top of an already-`executed` money action (the hold exists only once execution succeeded, tracking a second, later lifecycle: held → captured/refunded/expired) — a stranded reservation isn't a second thing that happens to a money action; it's a money action's own `status: "allowed"` row that simply never got resolved. Every field a release needs (`capId` resolvable via `agentId`, `variantId`/`offerId`/`cartId`, `amountPaise`, `quantity`) already lives on `money_actions` itself. A second table would have needed its own row created at reservation time and deleted or resolved at settlement time — real write traffic on every single purchase attempt, allowed or not, duplicating information the existing row already carries, purely to mirror a pattern that fit a different shape of problem.
**Cost:** `money_actions` gains a column that is `null` on every row except the brief window between reservation and settlement — a real, if small, amount of schema surface that's meaningless outside that window. A partial index (`WHERE status = 'allowed' AND reservation_expires_at IS NOT NULL`) keeps the sweep query cheap regardless of total table growth, the same mitigation `escrow_holds`' own index-free small table didn't need but this shared, much larger table does.

### The read-to-purchase ratio is a running lifetime counter, not a rolling window
**Context:** the Guardian's existing five signals (velocity, denied ratio, retry-same-target, escalation rate, AI-spend rate) are all computed over a rolling `RECENT_WINDOW_MINUTES`/`BASELINE_WINDOW_DAYS` pair via real-time SQL percentile queries — the established pattern for "is this normal right now." L23-3's read-to-purchase ratio could have followed that same shape.
**Options:** A rolling-window ratio, computed live the same way the other five Guardian signals are (reads and purchases both counted only within a trailing window); a simple lifetime running counter (`agents.catalogueReadCount`, incremented forever) divided by a lifetime count of `money_actions` rows.
**Chose:** the lifetime counter.
**Because:** the other five Guardian signals answer "is this agent behaving anomalously right now," which is inherently a windowed question — a burst is a burst only relative to a recent baseline. "Is this agent mostly a shopper or mostly a scraper" is a different, slower question a merchant asks about an agent's whole relationship with their catalogue, not a moment-to-moment anomaly; a lifetime ratio answers that more honestly than a windowed one would, and it's far cheaper to compute (one integer column read, versus a live SQL aggregation across `money_actions` bucketed by time). Money_actions' own `createdAt` timestamps mean a merchant who wants a windowed view can already get one by filtering the audit trail directly — this signal isn't the only way to ask a time-scoped version of the same question.
**Cost:** stated plainly in ARCHITECTURE.md's "What's deliberately not here yet" — an agent that browsed heavily once, long ago, and now purchases normally still carries that history in its denominator forever, with no time-decay. Acceptable for a surfacing-only signal a merchant reviews and can dismiss; would need revisiting if this signal were ever promoted to something that gates a request automatically (which L23-3 explicitly rules out doing).

## Layer 26 — Hardening

### Postgres over Redis for the distributed rate limiter
**Context:** rate-limit.ts's in-memory Map explicitly documented itself as not a substitute for a real distributed limiter. Fixing it for real needs some form of shared state across instances.
**Options:** Redis (a managed instance, e.g. Upstash's free tier) as a dedicated cache/counter store; Postgres, via a new table and the same atomic conditional-`UPDATE`/upsert pattern this codebase already uses for `spend_caps`, `product_variants`, and `agent_tasks`.
**Chose:** Postgres.
**Because:** this is the same reasoning Layer 17 already applied once to reject Temporal/BullMQ/Kafka for the task runtime, and Layer 13 applied before that: a table plus an atomic conditional write is a real, durable, transactional primitive this project already knows how to prove correct under concurrency, and it adds no new infrastructure, no new free-tier ceiling, and no new failure mode to a deployment that must stay on free tiers. A rate limiter's own state is tiny and short-lived — exactly the shape Postgres handles well with an indexed upsert, and reusing the database already in the request path is strictly simpler than adding a second stateful service whose own outage would need its own fail-open/fail-closed decision.
**Cost:** a real per-request database round trip on every rate-limited call, where Redis would be faster in the common case. Accepted: every existing conditional-write bound in this codebase (spend caps, stock, tasks) already pays this same cost, the query is single-statement and indexed, and the alternative (Redis) buys latency at the cost of a second infrastructure dependency this project doesn't otherwise need.

### Login throttling is decaying exponential backoff, never an account lockout
**Context:** the login path was already IP-rate-limited, which misses the distributed case — many IPs, one targeted account, the shape a real credential-stuffing run takes.
**Options:** A hard lockout after N failed attempts (locked until a merchant support action, or a fixed cooldown); a decaying, capped exponential backoff with a free-attempts floor.
**Chose:** the decaying backoff — never a lockout.
**Because:** a lockout hands an attacker a denial-of-service tool aimed at the merchant, not at this platform: anyone who knows a merchant's email can fail a login a few times on purpose and lock that merchant out of their own dashboard, which is worse than the credential-stuffing risk it defends against, especially for a merchant who may need dashboard access during a live payment incident. It also inverts this codebase's own "silence is not consent" principle (already established for escalations and negotiations) — an attacker's own action would become a decision the merchant never made, applied here to account access instead of money. A capped, decaying backoff destroys the economics of a genuine high-throughput credential-stuffing run while costing a real owner at most tens of seconds, and guarantees there is no input that produces a permanent stuck state.
**Cost:** a sufficiently patient, low-and-slow attacker (well under the backoff's effective rate) is throttled less aggressively than a hard lockout would throttle them. Accepted: that attacker is uneconomical for credential stuffing regardless (the whole point of stuffing is trying many accounts fast), and the constant-time comparison plus the separate IP-keyed rate limit close the more realistic gaps.

### The rate limiter fails closed on its own query error
**Context:** the plan's own requirement: "a limiter failure must fail closed for abuse but must not take down the site."
**Options:** On a DB error, allow the request through (treat the guard as advisory); deny the request and log it (treat the guard as load-bearing).
**Chose:** deny.
**Because:** CLAUDE.md rule 4 ("fail closed") already governs every money decision in this codebase; the endpoints this limiter guards either spend money directly (`/api/checkout/*`, `/api/agent/purchase`) or call a billed LLM on every request (`/api/chat`) — a broken rate limiter is exactly a case where "ambiguous state" should deny, not default to allowing unlimited traffic through. The alternative reasoning (a broken limiter shouldn't take the site down) is real but doesn't require allowing through — it requires the rest of the request path to keep working for every *other* route, which it does; only the specific rate-limited call is affected.
**Cost:** a genuine, temporary database outage degrades every rate-limited endpoint to fully refused rather than fully open, for as long as the outage lasts. Accepted as the correct direction explicitly, per the plan's own reasoning — a merchant losing checkout availability during a DB outage is a real cost, but it is a smaller cost than an attacker getting unlimited free LLM calls or unbounded checkout attempts during the same outage.

### Demo/judge access is a signed magic link, not a hardcoded auth exemption
**Context:** the throttle only engages after repeated login failures, so a judge typing the correct password is never delayed — but a real operational escape hatch was still worth considering for any edge case (a mistyped password during a live demo, for instance).
**Options:** A hardcoded exempt email address baked into the login path; an environment-variable allowlist (`AUTH_THROTTLE_EXEMPT_EMAILS`); a signed, time-limited, single-use magic link that bypasses the password step entirely for a demo session.
**Chose:** the magic link is the primary answer for judge/demo access; the environment-variable allowlist exists as a secondary, deployment-configurable escape hatch, never a hardcoded address.
**Because:** a hardcoded exempt email compiled into the source is a public-repo backdoor, and reads as one to exactly the people scoring this project — the plan calls this out explicitly as the thing hardening work must never quietly introduce. A magic link is strictly better than any bypass: it removes the login step for a specific, time-boxed, single-use grant rather than weakening the login step itself for everyone who happens to know one address. The environment-variable allowlist is kept only because it is easy to reason about, auditable (its use is logged loudly), configurable per deployment without a code change, and — critically — absent from the repository itself.
**Cost:** the magic-link mechanism is additional surface to build and hand to judges (a link, not just a password), rather than the zero-effort path a hardcoded exemption would have been. Accepted — the effort difference is small and the alternative is a real credibility risk in a security-hardening layer specifically. Note: the magic-link mechanism itself is not yet built as of this task — the allowlist exists now; the link is the recommended follow-on before a live judged demo.

### The dashboard/store CSP allows `'unsafe-inline'` for script/style, not a nonce
**Context:** a real Content-Security-Policy needed to exist on the dashboard without breaking it — Next.js's own app-router hydration payload ships an inline script on every page, and Tailwind's utility classes rely on inline `style` attributes in a few places.
**Options:** A strict CSP with a per-request nonce threaded through every Server Component that needs an inline script/style; a CSP with `'unsafe-inline'` on `script-src`/`style-src` specifically, keeping every other directive strict.
**Chose:** `'unsafe-inline'` for script/style only.
**Because:** nonce-per-request wiring through Next's App Router (Server Components, streaming, no central place every page's HTML passes through) is real, non-trivial infrastructure this stack doesn't have, and building it wasn't the point of this task — the point was closing the "no security headers at all" gap, and the directives that carry this layer's actual real risk (`frame-ancestors`, `object-src`, `base-uri`) are untouched by this compromise. `'unsafe-inline'` does weaken script-injection defense specifically, which is an honest, named limitation rather than a hidden one.
**Cost:** an XSS vector that could inject an inline `<script>` tag would not be blocked by this CSP alone (though it would still need to find an actual injection point — this CSP is not the only defense against that). A genuine nonce-based hardening pass is a real, scoped follow-on, not this layer — see ARCHITECTURE.md's "What's deliberately not here yet."

## Layer 21 — The protocol surface and proof of agency

### The `.well-known` root document is a merchant directory, not a resolved default
**Context:** L21-1 needed to add discovery at the conventional origin-root location, but this deployment is genuinely multi-tenant on one origin — there is no single "the merchant" the root path could mean.
**Options:** A query parameter (`?merchant=<id>`) resolving to one merchant's document; a subdomain-per-merchant scheme; a document at the root listing every merchant this origin serves, each pointing at its own real per-merchant manifest.
**Chose:** the directory.
**Because:** the plan's own instruction was explicit — a directory is truthful under multi-tenancy in a way "the default merchant" is not, and the alternatives both smuggle in a fabricated single-tenant assumption this codebase has deliberately avoided since Layer 2's merchant-onboarding pass removed the original hardcoded-demo-merchant shortcut. A query param also fails the "conventional location a crawler probes first" goal, since nothing about `/.well-known/agent-commerce.json` on its own suggests it needs a parameter. The directory costs nothing extra to build (one query already available via `storefront-catalogue.ts`'s existing shape) and degrades gracefully: zero connected merchants is an honest empty list, not an error.
**Cost:** an agent that wants one specific merchant now takes two hops (the directory, then that merchant's manifest) instead of one. Accepted — the per-merchant manifest's own URL is unchanged and still works directly for anyone who already knows a merchant id, which is the common real case (an agent arriving via a storefront link).

### 402 for unauthenticated, 200 for denied — two different questions, not a contradiction
**Context:** the existing, load-bearing rule is "a denial is HTTP 200 with a reason" — an authenticated agent needs to distinguish "you are over budget" from "the server broke." L21-3 asked for an x402-shaped challenge on an unauthenticated purchase attempt, which risked reading as a contradiction of that rule if not stated carefully.
**Options:** Keep every non-2xx response, including no-auth, as some flavor of denial-shaped body at 200; introduce 402 specifically for the no-identity case and document the distinction explicitly at the code site.
**Chose:** 402 for no valid bearer key, 200 unchanged for every authenticated outcome including a real gate denial.
**Because:** these are genuinely different questions. "Was this purchase allowed?" is a question the gate can only answer once an agent identity exists to evaluate a bound against — a request with no valid key never reaches that question at all, so answering it with the denial shape would be dishonest (a `boundApplied` and a checked-then-refused reason for a check that never actually ran). x402 exists precisely so a machine client can discover a price and a payment path without a human in the loop; 402 is the correct, standard signal for "you have not yet demonstrated you can pay," distinct from "you tried to pay and were refused." Documented directly in the route's own comment at the branch, since the two look similar enough at a glance that the next person to read the code could otherwise conclude they contradict each other.
**Cost:** none identified — the two paths are mutually exclusive by construction (the 402 branch returns before an agent is ever resolved) and no existing test or caller needed to change its assumptions about the 200-denial contract.

### "Documented subset" means: name the exact mechanism, name what's absent, never the bare protocol name
**Context:** the manifest previously disclaimed all conformance rather than describing what was actually built (Layer 13-3's real AP2 mandate verification, and this layer's own x402 challenge shape) — silence rather than honest specificity.
**Options:** Claim conformance to AP2/x402 outright (fastest to write, wrong); keep the blanket no-conformance disclaimer even though it's now stale for two of the four named protocols; state the exact mechanism implemented and the exact mechanism NOT implemented, every time the protocol's name appears.
**Chose:** the third option, applied everywhere: `discovery-manifest.ts`, the manifest route's own header comment, and this file.
**Because:** CLAUDE.md's own design conventions and this layer's governing rule both name the same failure mode — an agent that follows an advertised capability and finds nothing there does more damage than silence would have. "AP2" alone implies the full W3C Verifiable Credential/SD-JWT stack with selective disclosure, which this project does not have; saying so plainly, in the same sentence as what IS real (ES256-signed Checkout/Payment Mandate JWTs, verified before `checkBounds`), lets a counterparty's own integration code make a correct decision about what to rely on. The same reasoning applies to x402 (a 402 challenge shape, not a settlement protocol) and to ACP/NPCI UAP, which are named only as explicitly NOT implemented, since the hackathon brief mentions them as context.
**Cost:** more verbose manifest fields and doc comments than a bare `"ap2": true` would be. Accepted — the alternative is a claim that breaks on the first real integration attempt, which costs far more than the extra words.

### `unknownAgentsAllowed`/`newAgentOrderCeilingPaise` scope to self-registered agents only
**Context:** the first implementation of this bound applied to any agent with zero completed purchases, defaulting to deny when no `merchant_agent_terms` row existed — which denied every existing merchant-issued agent's very first purchase the moment this shipped, breaking six existing tests immediately (caught before merge, not after — see FAILURES.md).
**Options:** Keep the check unscoped (any new agent) but flip the default to permissive when unpublished; scope the check to `registrationSource: "self_registered"` agents only, leaving merchant-issued agents completely untouched regardless of terms.
**Chose:** scope to self-registered agents.
**Because:** a merchant who creates an agent by hand from their own dashboard has already vetted it by definition — it was never "unknown" in any sense this bound is meant to capture. "Unknown agent" names exactly the population L21-8's self-registration path creates: a stranger's agent this merchant has never seen before. Flipping the default to permissive instead would have weakened the "absence is real, not permissive" discipline this codebase applies everywhere else (`merchant_policies`, `merchant_reward_settings`) for the sake of avoiding a scoping fix that was more correct anyway.
**Cost:** none — this is strictly more correct than the first attempt, and every existing test suite (gate.test.ts, purchase route tests, MCP route tests) continues to exercise merchant-issued agents completely unaffected by this layer.

### The Refusal Receipt reuses `mandates.ts`'s keypair; it is never a second signing path
**Context:** L21-6 needed a way to sign a portable, verifiable receipt over a gate decision. A merchant already has exactly one ES256 keypair, generated lazily by `mandates.ts`'s `getOrCreateMandateKeypair()` and already published (in part) by L21-2's manifest.
**Options:** Generate a second, receipt-specific keypair; reuse the existing mandate keypair for receipts too.
**Chose:** reuse.
**Because:** the plan states this directly — one place in this codebase signs things, and it stays that way. A second key would mean the manifest has to publish two public keys instead of one, a counterparty has to know which key verifies which artifact, and this codebase would own two keypair-lifecycle stories (rotation, encryption, loss) instead of one. Reusing the same key also makes the "real round trip" test (sign a receipt, fetch the SAME published key over HTTP, verify) a genuine proof that the advertised key, the mandate-signing path, and the receipt-signing path are the same system — a second key would only prove a receipt verifies against itself, which is a much weaker claim.
**Cost:** a merchant's mandate keypair now has two consumers (mandates, receipts) instead of one, so a future key-rotation story needs to consider both. Accepted — no rotation mechanism exists yet for either consumer, so this is a cost paid once, later, not now.

## Layer 25 — Control surfaces

### Suspend every agent, never revoke, on the Kill Switch
**Context:** L25-2 needed one action that stops all money movement immediately. `agents.status` has exactly two values, `active` and `revoked` — revocation is a real, separate mechanism already used for a merchant deliberately cutting off one specific agent's integration for good.
**Options:** Set every active agent's `agents.status` to `revoked`; move every active agent's Guardian state (`agent_guardian_state.state`) to `suspended`, the same state the Runtime Guardian itself already uses for an automatic breach.
**Chose:** suspend via Guardian state, never touch `agents.status`.
**Because:** revocation is destructive by design elsewhere in this codebase — reactivating a revoked agent is a deliberate, separate merchant action, and nothing about "I panicked and want everything to stop for a moment" should cost a merchant their entire integration's identity if they later realize the freeze wasn't needed, or need to lift it in thirty seconds during a live incident. Suspension via Guardian state is exactly as effective at stopping money (`resolveGuardianBound` already denies a suspended agent outright in `checkBounds`, before any budget is reserved) and is trivially, instantly reversible — the property the plan calls out explicitly ("must never make the Kill Switch hard to reverse"). It also means the Kill Switch adds zero new bounds: it is a bulk write to a table the Guardian already owns, evaluated by code that already exists.
**Cost:** none identified — this is strictly the safer and cheaper choice on every axis the plan names.

### The Bound Simulator replays real history; it never forecasts
**Context:** L25-1's stated purpose is answering "what would a different cap have meant for my business" — the tempting easy version of that answer is a revenue projection ("you'd have made ₹X more").
**Options:** Compute a revenue estimate assuming every recovered denial becomes a completed sale; replay only what the deterministic bound arithmetic itself would have output for each real recorded attempt, with an explicit refusal to guess buyer behaviour.
**Chose:** replay only.
**Because:** a denied buyer's actual next move — retry, buy less, or leave — is not observable from anything this codebase records, and inventing an assumption about it (even a conservative one) would be presenting a fabricated number as fact, the exact violation the design conventions' rule 14 names directly ("a plausible-looking number with no real query behind it"). The plan's own framing is also the stronger engineering argument: replay is possible, and trustworthy, *specifically because* the bounds are deterministic arithmetic — a model-based gate could never support this feature honestly, since replaying a model's judgment against a counterfactual input has no guarantee of matching what the model would actually have said. The simulator existing at all, and being replay rather than forecast, is itself evidence for the architecture.
**Cost:** the simulator cannot answer the question a merchant most wants asked ("would this have made me more money") — only the narrower, honest one ("would this specific bound have allowed more of what was actually attempted"). Accepted as the correct tradeoff; the UI states this limitation directly rather than hiding it.

### The Trust Score is a read-layer figure; nothing here changes if that ever seems tempting
**Context:** L25-3's plan states the rule ("never read by gate.ts") as firmly as any rule in this codebase, and asks what would have to be true for that to change.
**Options considered, and rejected in the plan's own terms:** an auto-suspend threshold on a low score; an auto-tightened cap for a low-scoring agent; a required-mandate-above-value keyed to trust score instead of a flat merchant-configured amount.
**Chose:** none of the above — trust score is display-only, forever, by design.
**Because:** every one of those options would make an aggregate, derived-from-history figure into the thing deciding whether money moves — exactly the CLAUDE.md rule 2 violation the plan calls out by name, and structurally identical to what would happen if a model's own confidence score were wired into `checkBounds`. A trust score is a summary computed AFTER the fact from bounds that already ran; feeding it back into those same bounds creates a loop where past denials shape future denials through a channel no merchant configured and no audit entry could name honestly (`boundApplied: "trust_score"` would describe an aggregate, not a rule a merchant set). **The honest answer to "what would have to be true for this to change" is: nothing.** A merchant is always free to read the score and manually tighten a cap or revoke a key themselves — that decision is real, deliberate, and attributable to them. The gate reading the score directly is not a bigger version of that; it is a categorically different thing this project has decided not to build.
**Cost:** a merchant who wants "automatically be more careful with low-trust agents" doesn't get it built-in. Accepted — that automation is exactly the kind of opaque, unaccountable money decision this project's entire premise argues against.

### A decision's public share is a token, not the audit_log id itself
**Context:** L25-4 needed to let a merchant share one specific decision outside the dashboard — a genuinely useful demo/support artifact — without making every decision guessable-and-public by its id.
**Options:** Make `/why/[id]` publicly readable for anyone who has (or guesses) an `audit_log` UUID; require a merchant session for every view, with no public path at all; require a merchant session by default, with an explicit, separately-generated, revocable token as the only opt-in exception.
**Chose:** the third option.
**Because:** a decision references a real agent's real activity and, for the risk-escalation path, real risk-assessment reasoning — treating it as public by default the moment its id is known would be a real information leak, and UUIDs are not a secret (this codebase's own `isolation.test.ts` exists specifically because ids are assumed guessable). A bare "public if you know the id" design also can't be revoked — the id never changes. A separate, opaque, database-backed token can be minted deliberately, listed, and revoked independently of the decision itself, which is what "explicit and revocable" (the plan's own words) actually requires.
**Cost:** one extra table (`decision_share_tokens`) and one extra step (mint, then share the URL) versus a bare link. Accepted — the alternative's blast radius (every past and future decision effectively public) is not a reasonable tradeoff for saving one click.

### A return request is a new table, not a reuse of `escalations`
**Context:** L22-1 needed a place to store a return request against a completed purchase, and `escalations` already exists for "a purchase is pending, a human needs to decide."
**Options:** Reuse `escalations` with a new `outcome` value or a nullable-`moneyActionId`-means-return convention; add a new table, `return_requests`.
**Chose:** a new table.
**Because:** `escalations.moneyActionId` always references a money action that is still *pending* — the row exists specifically so the existing escalation-expiry sweep (`notifications/expiry.ts`) can find and auto-deny it. A return request references a purchase that already *completed* (captured), and forcing one table to serve both shapes would mean either weakening that sweep's own query (it would need to distinguish "pending because awaiting a first decision" from "pending because awaiting a return decision," which are different lifecycles with different expiry semantics) or duplicating the sweep entirely and accepting the risk of the two silently diverging. A return request also carries fields an escalation has no concept of at all — a stated buyer reason, a model-generated summary/recommendation, and a `declined_by_desk` terminal state escalations never reach. Two tables that answer genuinely different questions, kept separate, is cheaper than one table straining to answer both.
**Cost:** some duplicated shape (both tables have a status enum, an `expiresAt`, a resolving actor) — accepted, matching this codebase's own precedent of duplicating the `ReadinessCheck` shape rather than forcing one scorer to read two different kinds of evidence.

### `declined_by_desk` and `rejected` are different status values, not the same "no" collapsed
**Context:** Both a model declining to forward a claim and a merchant rejecting one end with the buyer not getting a refund. A simpler schema would use one `rejected` value for both.
**Options:** One terminal refusal value (`rejected`) regardless of who refused; two distinct values naming who actually made the call.
**Chose:** two distinct values.
**Because:** this is the same reasoning `negotiations.status` and the Agent Runtime's `pending`/`waiting` split already established in this codebase: collapsing "the desk declined it" into "the merchant rejected it" misattributes a decision to a human who never saw the request at all. A merchant reading their own dashboard, or an agent polling `get_return_status`, needs to be able to tell "I decided no" from "a model filtered this out before I ever looked" — the two carry different implications about whether the merchant should go look at what got filtered, and conflating them would make the desk's own filtering invisible and unauditable.
**Cost:** one more enum value, and dashboard/reporting code has one more case to handle. Accepted — the alternative actively hides a fact this project's whole audit-trail discipline exists to surface.

### No auto-approval threshold, at any amount — the AI can only ever narrow the door, never open it
**Context:** The obvious next question once a returns desk exists: "can small refunds just go through automatically?" A ₹50 return costs more in merchant attention than the money at stake.
**Options:** A merchant-configurable auto-approve ceiling ("anything under ₹X approves without a click"); no auto-approval path at all, at any amount, ever.
**Chose:** no auto-approval path, named explicitly in the plan as "deliberately not built" so a future layer has to argue for it rather than assume it.
**Because:** this is CLAUDE.md rule 2 in its sharpest form — a refund is a money action, and "whether a refund is issued at all" sits in the deterministic-code-only column, never the model's. An auto-approve threshold, even a merchant-configured one, would mean the model's own read of a conversation (however that gets scored) is the thing that actually decides some refunds go out — the exact asymmetry this layer is built to prevent, stated in the plan as "the AI can filter out a request, but it can never let one through." A threshold also can't be evaluated honestly without the model first judging the claim is legitimate, which reintroduces model judgment into the approval path by the back door even if the dollar check itself is deterministic.
**Cost:** every return, including a trivially small and obviously legitimate one, costs a merchant one real click. Accepted — the plan is explicit that this is the correct cost of the safety property, and a merchant who wants less clicking can filter their own queue by amount without this codebase building an unsafe shortcut for them.

### The asymmetry rule traces directly to `model-armor.ts` and `risk.ts`, not invented fresh for this layer
**Context:** L22's central safety property — "the model can decline, never approve" — needed grounding in something more than "this seemed safest," since a judge is explicitly scoring where AI judgment was and wasn't trusted.
**Options:** Treat this as a new, layer-specific rule; explicitly derive it from patterns this codebase already ships and already tests.
**Chose:** explicit derivation.
**Because:** `model-armor.ts` already states "may only block, never approve" as its own governing rule for inbound/outbound scanning, and `gate.ts`'s risk layer already enforces "risk can only downgrade a decision, never approve past a deny." Both are the identical shape: a model's negative judgment is trusted to narrow what happens next; a model's positive judgment is never trusted to widen it. Recognizing the returns desk as a third instance of the same pattern — rather than a bespoke new safety argument — means the property can be tested the same proven way (a static import check plus a behavioural equivalence/isolation test), and means a reader who already understands `model-armor.ts` immediately understands why this layer is shaped the way it is.
**Cost:** none — this is free consistency, and it's the stronger design argument, not a weaker one.

## Layer 20 — the merchant CLI (`thirdman`)

### `cli/`'s AuditCheck shape duplicates `agent-readiness.ts`'s ReadinessCheck deliberately
**Context:** L20-3's audit answers "is this store AI-buyer-ready" the same question `agent-readiness.ts` already answers from database rows — the plan explicitly asks whether the two should share code.
**Options:** Have the CLI import `agent-readiness.ts` and adapt it to filesystem evidence; keep the CLI fully standalone (its own `AuditCheck`/`AuditReport` types, no import of `src/lib` at all) and match only the shape.
**Chose:** standalone, shape-only duplication — the same choice this codebase already made once for `return_requests` vs. `escalations` (see the Layer 22 entry above).
**Because:** `agent-readiness.ts` runs against real database rows inside a live merchant session; `cli/` is a separate published package with no database connection, no session, and no import boundary into `src/lib` at all — forcing one module to read both a Drizzle result set and a filesystem listing would mean an artificial abstraction with no shared logic underneath it, just a shared shape. Keeping the interface (`id`/`label`/`weight`/`passed`/`fix`) identical is what actually matters: a merchant reading both the dashboard's Readiness page and the CLI's audit output sees one product's voice, not two competing scorers.
**Cost:** two files maintain a parallel interface by convention, not by the compiler. Accepted, matching the L22 precedent exactly — a judge reviewing the checklist logic in either file understands the other's without a second read.

### Account linking is a pasted one-time token, not a local-callback browser handoff
**Context:** L20-6's plan describes "the CLI opens the dashboard, the merchant approves, the CLI receives a scoped token" — full OAuth-shaped local-callback flow (spin up a localhost server, open a browser, handle the redirect). Building that is real new infrastructure: a CSRF/state parameter, a port to bind, a timeout, and a second auth surface this codebase would then have to keep secure indefinitely.
**Options:** Build the full local-callback browser handoff described in the plan; a merchant generates a short-lived, single-use token on a new `/dashboard/cli` page and pastes it into the terminal when `init` asks.
**Chose:** the pasted token, confirmed with the user directly before building (this session's own transcript) rather than assumed.
**Because:** the property that actually matters — a password never touches the terminal — holds identically either way. The pasted-token version reuses `decision-share.ts`'s exact pattern (an opaque, single-use, short-lived, database-backed token) rather than inventing a new authentication surface, and is dramatically less code to get right and keep secure. The full browser-handoff flow is a legitimate future upgrade if `thirdman` grows a larger installed base where "one more terminal paste" becomes real friction, but it is not free, and the plan's actual requirement (no password in the terminal) does not require it.
**Cost:** one extra manual step (open the dashboard, click generate, copy, paste) versus a fully automated handoff. Accepted — the user explicitly chose this tradeoff when asked.

### The audit's model-summary step (L20-3) is a named gap this session, not a silent one
**Context:** L20-3 names "the model's one legitimate job in the audit" — turning structured findings into plain-English prose — and specifies it must degrade to no prose (never a missing audit) on failure.
**Options:** Build a real call path this session (either a new CLI-facing proxy endpoint on the main app, or a direct provider call from the CLI using a merchant's own key); ship the audit with `summarizeFindings()` as an explicit seam that already implements the required degrade behavior, returning `null` unconditionally, and record the gap.
**Chose:** the explicit seam, no real call this session.
**Because:** there is no existing CLI-facing model-proxy endpoint on the main app, and building one plus a direct-provider path from a standalone, unauthenticated-by-default CLI package is real, separate scope — not a small addition to an already-large layer. Shipping a function that already has the exact required signature and already returns the documented safe-failure value means nothing downstream needs to change when this is wired up; it is strictly better than a half-built network call that might silently misbehave.
**Cost:** `init`/`audit` never show prose summary this session — only the structured checklist. Accepted, and named directly in PROGRESS.md/summarize.ts rather than left for a reader to discover.

### JSON-LD generation (the optional part of L20-5) was cut, not half-built
**Context:** The plan itself names this the first thing to cut if it can't be done cleanly: "a half-correct JSON-LD block is worse than none."
**Options:** Ship a heuristic that guesses at a merchant's product-page template shape and injects a JSON-LD block; skip it entirely this session.
**Chose:** skip, with the reasoning recorded in `cli/src/generate/json-ld.ts` itself.
**Because:** any heuristic good enough to inject correct `schema.org/Product` markup into an arbitrary, unknown React/Astro/PHP template would need real template parsing this session didn't have time to build safely — and the plan explicitly names a wrong guess here as worse than doing nothing. The discoverability audit still checks for and reports missing structured data; it just doesn't try to write it.
**Cost:** the discoverability score's structured-data check can only ever fail or already-pass, never be fixed by `init` itself. Accepted per the plan's own explicit instruction.

## Layer 24 — Onboarding surfaces

### A custom, unlisted Shopify app on a real dev store, not a listed one
**Context:** L24-3's plan states the scoping honesty up front: "a public App Store listing requires Shopify's review, whose timeline is outside this project's control." The submission needs a real, working Shopify integration to demonstrate, on a timeline a hackathon actually has.
**Options:** Submit the app to Shopify's App Store review and wait for approval before demoing; build and install a custom/unlisted app directly on a real Shopify development store, which needs no review at all.
**Chose:** the custom, unlisted app on a real dev store.
**Because:** Shopify's review process is a real gate this project has no control over the timing of, and a listed app buys nothing technical — a custom app installed on a dev store runs the identical OAuth authorization-code flow, the identical Admin API calls, the identical token storage, against Shopify's real production infrastructure. Every code path a listed app would exercise is exercised. The only thing missing is Shopify's own human review of the listing, which is a distribution decision, not an engineering one.
**Cost:** this cannot be installed by an arbitrary merchant from Shopify's App Store today — only on a store the reviewer/demoer controls or has been given collaborator access to. Stated plainly rather than implied: `README.md` and this entry both say "custom/unlisted app," never "listed on the Shopify App Store," because claiming a listing that doesn't exist is the kind of thing that unravels under one direct question.

### The Shopify catalogue sync lands in `catalogue-import.ts`'s existing pipeline, not a new write path
**Context:** Layer 5 already built CSV and pasted-text import, both ending in a merchant-confirmed preview before anything reaches `products`/`product_variants`. Shopify's Admin API is a third real source of the same kind of data.
**Options:** Give Shopify its own dedicated write path directly into the catalogue tables, since its data is already structured (unlike a CSV row that might be malformed, or a pasted blob that needs a model to extract); reuse `importCatalogueRows()` unchanged, adding `"shopify"` as a third value on the existing `catalogueImportSourceEnum`.
**Chose:** reuse, unchanged.
**Because:** "already structured" doesn't mean "already correct for this schema" — a Shopify variant can still have a missing SKU, a price that isn't a real number, or a duplicate SKU across the paginated result, and the existing pipeline already has the exact preview-then-confirm discipline and per-row error handling those cases need. A second write path would mean two places that could each individually drift from the schema's real constraints, and two places a future migration has to update instead of one. `fetchShopifyCatalogue()`'s only job is mapping Shopify's REST response into the same `ImportRowPreview` shape the other two sources already produce; `confirmShopifySync()` calls `importCatalogueRows()` unchanged.
**Cost:** none identified — this is strictly a smaller diff than a second writer would have been, and it inherits `MAX_IMPORT_ROWS` and the SKU-collision handling for free.

### The Shopify install's CSRF state is a database row, not a cookie
**Context:** Google/GitHub OAuth (Layer 12) already solved "state must survive the round trip to a third party and back" with a short-lived `httpOnly` cookie (`oauth.ts`'s `OAUTH_STATE_COOKIE`). Shopify's install flow looks superficially identical.
**Options:** Reuse the same cookie-based state pattern; store the state as a row in a new table (`shopify_install_states`), matching `cli_link_tokens`'/`decision_share_tokens`'s shape instead.
**Chose:** a database row.
**Because:** Google and GitHub's OAuth redirect goes straight from this app to the provider's login page and back — one continuous browser session, so a cookie set right before the redirect is still present when the callback lands. Shopify's install additionally routes through the *merchant's own Shopify admin*, where the merchant approves scopes inside Shopify's own UI before Shopify redirects back — a real intermediate hop through a third party's own multi-step flow, not guaranteed to preserve every cookie the way a single external-IdP redirect does. A row keyed by an unguessable random state value survives that regardless of cookie behavior, and costs nothing extra to build since `cli_link_tokens` already established the exact shape (single-use, short-lived, deleted on redemption).
**Cost:** one more table and one more sweep (`sweepExpiredShopifyInstallStates()`) than a cookie would have needed. Accepted — the alternative is a real, silent failure mode (a merchant approves the install and lands back on an error) that would be hard to reproduce and debug later.

### The paste-a-prompt integration path is a spec for a human, never an instruction for an AI to edit a live store
**Context:** L24-6's own "what this layer must not do" names this directly: "Shopify's Sidekick is not a theme-code editor and WordPress has no first-party AI editor; a paste-a-prompt flow is a lottery whose losing outcome is a half-modified live storefront that reports itself as ready."
**Options:** For an unrecognised platform, generate a prompt the merchant pastes into whatever AI assistant their platform offers, framed as "ask your AI to do this"; generate a precise written specification framed as "give this to a developer, or to whatever assistant you trust, and review the result yourself" — the same content, a different frame and a different implied reviewer.
**Chose:** the spec, framed for a human reviewer.
**Because:** the distinguishing property is not what the text says, it's who is expected to check the result. A prompt handed to an AI editor implies the AI's output is trustworthy enough to ship unreviewed — which is false for a live storefront serving real customers, and is exactly the mechanism this layer's own governing rule (reads freely, writes only what's approved) exists to prevent everywhere else. A spec handed to a human developer carries the opposite implication: review before you ship. `unsupported-platform-spec.ts`'s generated document says outright that this path is unverified by Thirdman and that `thirdman doctor` is the way to check the real result once implemented.
**Cost:** a merchant with no developer and no platform-specific integration gets a document to hand someone, not a one-click fix. Accepted — the alternative (a paste-a-prompt flow) trades that inconvenience for a real risk to a live store, which this codebase does not do anywhere else either.

### The setup conversation drafts a proposal; a separate module writes it, and the drafting module cannot import the writer
**Context:** L24-7 replaces a tedious per-agent form with a conversation, but the form already enforces deny-by-default capabilities and a merchant-set cap — the exact discipline a chat-driven flow could accidentally erode if the model's output ever reached a row directly.
**Options:** Let `draftSetupProposal()` write the proposed agents directly once the merchant approves the conversation (fewer moving parts, one function does both jobs); split drafting (`setup-conversation.ts`) and writing (`setup-conversation-confirm.ts`) into two modules, with the drafting module never importing the writer.
**Chose:** the split, with the import boundary enforced and asserted by a test.
**Because:** this is the same shape `reward-rules.ts` (Layer 14) and `catalogue-import.ts` (Layer 5) already proved out — draft → zod-validate → confirm — and this codebase has now built the identical isolation proof five times (memory, the Trust Score, the returns desk, the buyer agent, and now this) because it is the one guarantee worth re-verifying structurally rather than trusting to code review: a model output, however persuasive, has no *code path* to a row, not just no *intended* one. A single combined function would still probably behave correctly, but "probably" is not the standard this codebase holds every other model-adjacent write to.
**Cost:** one more file and one more import boundary to maintain than a combined function would need. Accepted — `setup-conversation.isolation.test.ts` is a handful of lines and it is the difference between "we reviewed the code and it looks safe" and "this cannot happen, and here is the test that proves it."
