# FAILURES

Every real breakage, dead end, and wrong turn — logged as it happens.

## Why this file exists

The buildathon application asks: *"What broke, and how you got out."* Razorpay says this is **the answer they read first**.

These cannot be reconstructed later. A week from now the detail that made a bug interesting will be gone, and a reconstructed story reads as invented. Write the entry when it happens, before moving on.

## What to log

Log it if it cost real time or changed an approach:

- A bug that took more than a few minutes to understand
- An API that behaved differently than documented
- A design decision reversed after building it
- An integration that failed for a non-obvious reason
- A wrong assumption discovered late

Do not log routine typos or one-line syntax errors.

## Format

```
### <short title>
**When:** layer / task
**What happened:** the symptom, as first observed
**Why:** the actual root cause, once known
**Fix:** what resolved it
**Lesson:** what would prevent it next time — omit if there isn't one
```

Be specific. "Webhook didn't work" is useless. "Razorpay signs the raw request body, and Next.js had already parsed it to JSON, so recomputed HMACs never matched" is the answer they want to read.

### npm-installed CLI shims are POSIX shell scripts, not runnable by `node` directly
**When:** L0-2, L0-3
**What happened:** `node --env-file=.env.local ./node_modules/.bin/tsx ...` and the same pattern for `drizzle-kit` both threw `SyntaxError: missing ) after argument list` pointing at `basedir=$(dirname ...)` — the first line of the file.
**Why:** on Windows, npm's `node_modules/.bin/<tool>` entries are POSIX shell wrapper scripts (for bash/WSL), not JavaScript. `node` was trying to parse the shell script as JS. This only breaks when a tool is invoked via `node <path-to-bin>` instead of through npm's own dispatch (`npx`, or an `npm run` script without an explicit `node` prefix) or a package manager shim that resolves `.cmd`/`.ps1` variants.
**Fix:** invoke each package's actual JS entry point directly — `tsx/dist/cli.mjs` for tsx, `drizzle-kit/bin.cjs` for drizzle-kit — instead of the `.bin/` shim, so `node --env-file=.env.local <real-entry> ...` works cross-platform.
**Lesson:** on Windows, when reaching for `node --env-file=... ./node_modules/.bin/X`, check the package's `package.json` `bin` field for the real entry file first rather than assuming the `.bin/` path is directly node-executable.

### Assumed Gemini/Groq model names were stale
**When:** L0-6
**What happened:** `gemini-2.0-flash` returned a 404 — Gemini's own error message said the model "is no longer available," pointing to `gemini-3.6-flash`. Groq's `models.list()` didn't contain any obvious Llama chat model at all — the account's available list was mostly `gpt-oss`, `whisper`, and specialty models.
**Why:** LLM provider model catalogs move fast and deprecate old names outright rather than just marking them legacy. Hardcoding a model name from memory/training data is a bet that it still exists by the time the code runs.
**Fix:** wrote a throwaway probe script that called `groq.models.list()` and made a real `generateContent` call against the name Gemini's own error suggested, before committing to model names in the wrapper. Settled on `openai/gpt-oss-20b` (Groq) and `gemini-3.6-flash` (Gemini), both confirmed live.
**Lesson:** never hardcode a provider's model name from memory. Confirm it against a live call (or the provider's model-list endpoint) at implementation time, since these change on a timescale of weeks, not years.

### `@/` path alias silently fails inside a dynamic `import()`, only under tsx
**When:** L1-1, verifying the gate's atomic reservation under real concurrency
**What happened:** a stress test firing 20 truly concurrent purchase attempts against a cap sized for 5 came back with 0 allowed, 20 denied. The failure reason for every one was `Cannot find package '@/lib' imported from .../gate.ts`.
**Why:** `gate.ts` used `const { createOrder } = await import("@/lib/razorpay")` instead of a static top-level import, on the mistaken assumption this avoided some circular-import risk. tsx's compile step resolves the `@/*` path alias for static imports, but a dynamic `import()` call is resolved by Node itself at runtime, which has never heard of the alias and fails to find the module. The error surfaced as "execution failed," which the gate correctly treated as a money-action failure and released the reserved budget for — so the *bound-checking* logic looked broken (0 allowed) when the actual bug was one level lower, in module resolution.
**Fix:** changed to a static `import { createOrder, RazorpayCallError } from "@/lib/razorpay"` at the top of the file, matching every other module in the codebase. No circular import existed — the dynamic import was unnecessary defensiveness.
**Lesson:** never use a dynamic `import()` with the `@/` alias under tsx; it will not resolve. If a dynamic import is genuinely needed, use a relative path. More generally: a stress/mutation test surfaced this immediately because it exercised the real execution path under load — the mocked vitest unit tests never would have caught it, since the mock intercepts `createOrder` before module resolution matters. Worth remembering when deciding what "verified" means for a money path.

### postgres-js mis-binds a raw `Date` parameter mixed with a uuid-typed parameter in the same `sql\`\`` template
**When:** L13-4, the Runtime Guardian's `computeGuardianSignals()`
**What happened:** every one of `guardian.test.ts`'s real-DB tests failed with `TypeError: The "string" argument must be of type string or an instance of Buffer or ArrayBuffer. Received an instance of Date`, thrown deep inside `postgres`'s connection/Bind code, not application code. The query itself was syntactically correct SQL and worked fine when run manually.
**Why:** a raw `sql\`\`` template passing a JS `Date` object as one bind parameter alongside a plain string (an agent id, inferred as uuid-typed OID 2950) in the same prepared statement confused postgres-js's type inference for the Bind step — it tried to serialize the Date the same way it serializes the uuid-typed string, which fails. This never surfaces through drizzle's query-builder helpers (`gte`/`lte`/`eq` against a `timestamp` column, used everywhere else in this codebase — e.g. `risk.ts`'s `computeRiskSignals`) because those never hand a raw `Date` into a hand-written `sql\`\`` template; it only bites hand-rolled SQL with `percentile_cont`/CTEs, which the Guardian's baseline computation genuinely needed.
**Fix:** convert every `Date` to `.toISOString()` before interpolating into a raw `sql\`\`` template, and cast the column comparison explicitly (`created_at >= ${isoString}::timestamptz`) so Postgres parses the string as a timestamp rather than relying on inferred parameter typing.
**Lesson:** never pass a raw `Date` object into a hand-written `sql\`\`` template in this codebase — always `.toISOString()` it first with an explicit `::timestamptz` cast on the SQL side. Prefer drizzle's query-builder date helpers (`gte`/`lte`) when the query doesn't need raw SQL at all; reach for raw `sql\`\`` only for genuinely SQL-only constructs like `percentile_cont`, and treat every Date parameter there as suspect. Caught immediately because `gate.properties.test.ts`'s and `guardian.test.ts`'s own DB-backed tests exercise the real query, not a mock — the same "a stress/mutation test against the real path catches what a mock can't" lesson as the entry above.

### `db.execute(sql...)` cleanup in a demo script must delete `audit_log` before `money_actions`, and by-agent scoping needs two predicates
**When:** L13-6, `scripts/demo-failure-guardian-trip.ts`
**What happened:** the demo's own scenario ran correctly end to end (all 7 steps, both real evaluations, the real denial, the real notification, the real re-arm), then the script's `finally` cleanup block itself threw `PostgresError: update or delete on table "money_actions" violates foreign key constraint "audit_log_money_action_id_money_actions_id_fk"` — a real FK violation, not a scenario failure, but still a nonzero exit code.
**Why:** the cleanup order deleted `money_actions` before `audit_log`, but `audit_log.money_action_id` FKs into `money_actions` — the real purchase created after re-arm (step 7) left a `money_action_executed` audit row referencing it, and that specific audit event (see `gate.ts`'s `executeAndSettle`) doesn't carry `metadata.agentId` the way most other audit events in this codebase do (`money_action_attempt:*`, `guardian_transition`, `agent_capability_denied` all do), so a naive "delete audit_log where metadata->>'agentId' = X" cleanup predicate would have missed that row even with correct ordering.
**Fix:** delete `audit_log` first, with a two-predicate `WHERE` — `metadata->>'agentId' = X OR money_action_id IN (SELECT id FROM money_actions WHERE agent_id = X)` — so both the metadata-tagged rows and the money-action-linked-but-untagged row are caught in one statement, before `money_actions` (and everything else) is deleted.
**Lesson:** this is the same FK-ordering class of bug FAILURES.md already records for L6-4 and L9's `reward-actions.test.ts` cleanup (delete the referencing table before the referenced one) — but the new wrinkle here is that not every audit event carries the same identifying metadata shape, so "delete by an assumed-present metadata field" is not a safe general cleanup strategy on its own; check what the specific event types a script actually produced actually carry before writing the delete predicate, or join through the money action id as a second path.

### `guardian.test.ts`'s own `afterEach` didn't clean up the real notification its suspension scenario wrote
**When:** L13-6, a full-repo regression run after Layer 13 landed
**What happened:** `guardian.test.ts` had passed 12/12 in every isolated run during development, but failed twice during a full-repo `vitest run` with `PostgresError: update or delete on table "merchants" violates foreign key constraint "notification_deliveries_merchant_id_merchants_id_fk"` — thrown from the test file's own `afterEach`, not the test body.
**Why:** `guardian.ts`'s `evaluateAndTransition()` enqueues a real merchant notification (`notification_deliveries` row) the moment an agent is actually suspended — added in the same commit as the Guardian's suspension logic itself. The test file's cleanup block was written and verified against earlier isolated runs *before* this notification-enqueue call existed in the version being tested, and was never re-checked against the final code. Every isolated run of this file up to that point genuinely did exercise the suspension path and genuinely did write the notification row — so the missing cleanup step was a real, reproducible bug from the moment the notification call was added, not something a full-suite run "caused." It simply wasn't re-verified until a full-repo run happened to be the next time this exact file ran.
**Fix:** added `await db.delete(schema.notificationDeliveries).where(eq(schema.notificationDeliveries.relatedEntityId, currentAgentId))` to `afterEach`, before the `guardian_transitions`/`agent_guardian_state`/`spend_caps` deletes — the same FK-ordering position `demo-failure-guardian-trip.ts`'s own cleanup already used correctly.
**Lesson:** when a new code path starts writing to a table as a side effect of what's under test (here: a notification fired by a state transition, not the primary thing the test asserts on), the test's cleanup block must be re-checked against that new side effect specifically — passing in isolation earlier in development is not evidence the cleanup is complete once new side effects land later in the same session. A full-repo regression run remains the only way this class of gap reliably surfaces, since a single file's own tests never assert on their own cleanup succeeding.

### Adding a deny-by-default authorization check breaks every pre-existing test agent created without a capability grant
**When:** L13-6, the same full-repo regression run
**What happened:** a full-repo `vitest run` reported 28 failed tests across 10 files immediately after L13-2 landed — `src/app/api/agent/purchase/route.test.ts` and `src/app/api/mcp/route.test.ts` both failed nearly every test, with reasons like `"This agent does not hold the purchase:create capability"` where the test expected a completely different denial (a per-transaction-max breach, an unknown SKU, a stock-exhaustion message) or an outright success.
**Why:** L13-2's `requireCapability()` check is deny-by-default and runs before any other route/tool logic — exactly as designed. But every pre-existing test file that creates an agent directly in the database (bypassing the dashboard's new capability-grant form entirely) had no way to know this new gate existed, so those agents were created with zero granted capabilities, same as any other freshly-created agent post-migration. The migration's backfill only covers agents that existed *before* the migration ran — a test agent inserted fresh by a test's own `beforeEach`/helper function is, correctly, a brand-new agent with nothing granted, and every test asserting on what happens *past* that check (price mismatches, stock, idempotency, spend cap arithmetic) never got there.
**Fix:** granted the relevant capability (or, for a shared helper backing many different capability-gated tool calls, the full capability set — mirroring the migration's own backfill) directly in each affected test file's agent-creation helper, plus added `agent_capabilities` cleanup to each file's `afterEach` (an FK into `agents` that must be deleted first).
**Lesson:** adding a new deny-by-default authorization layer is, by definition, a breaking change to every existing caller that never explicitly opted in — including test fixtures, which is easy to forget since "the code compiles and the new tests pass" doesn't surface it. The real signal only came from running the FULL suite, not just the new files' own tests — a lesson this session had to re-learn even after already having written a property-based test suite whose entire purpose was catching exactly this class of "does the new thing compose correctly with the old thing" gap; property tests cover the pure arithmetic, they don't cover "did every existing integration test remember to ask for the new permission."

### Unscoped `afterEach` deletes wiped rows across concurrently-running test files
**When:** L1-2, after switching every test to hit the real database with no mocks
**What happened:** running the full suite together produced a shifting set of failures each run — a spend cap that had just been created reported "no spend cap exists," an `escalation` lookup came back `undefined`, and separately a `delete from money_actions` failed with a foreign key violation against `audit_log`. Running any single file in isolation, everything passed.
**Why:** two separate bugs stacked. First, `gate.test.ts` and `gate.escalation.test.ts` both had an `afterEach` that ran `db.delete(schema.spendCaps)` and `db.delete(schema.escalations)` with no WHERE clause at all, deleting every row in those tables. vitest runs separate test files concurrently by default, so file A's cleanup was deleting file B's in-flight cap mid-test, and vice versa, in a nondeterministic order depending on which test happened to finish first. Second, after adding scoping I removed the `audit_log` delete entirely, reasoning the rows were harmless, without noticing `audit_log.money_action_id` has a foreign key onto `money_actions` — so leaving those rows behind then blocked deleting the `money_actions` rows they referenced, which is a different failure with the same symptom (an FK violation).
**Fix:** rewrote cleanup in both files to track only the agent ids (and by extension spend cap ids) created by that specific test, scope every delete to those ids or to the test's own merchant id, and delete `audit_log` rows referencing this test's `money_actions` before deleting the `money_actions` rows themselves. Also fixed the same unscoped-delete pattern in `audit.test.ts`, scoping it by event name instead.
**Lesson:** once tests share a single real database with no mocks, `afterEach`/`afterAll` cleanup is no longer "delete what I made," it's "delete exactly rows scoped to what I made, in FK dependency order" — and it must assume other test files are mutating the same tables concurrently at the same time. A cleanup query with no WHERE clause is a bug the moment more than one test file touches that table, even if it looks correct when that one file is run alone.

### drizzle wraps the real postgres error on `.cause`, not on the error itself
**When:** L1-3, implementing idempotent purchase requests
**What happened:** two genuinely concurrent requests with the same idempotency key were meant to have one win the unique-constraint insert and the other detect the violation and replay the winner's result. Instead the loser fell all the way through to the outer `catch (unexpectedErr)` and denied the request outright, with a message showing the raw SQL and params — proof the specific-error handling never matched.
**Why:** the code checked `err.code === "23505"`, which is correct for a raw `postgres.js` error, but drizzle's query layer wraps that error in its own object and puts the real `PostgresError` (with the actual `.code`) on `err.cause`, not on `err` directly. Checking the wrong location meant the unique-violation branch never triggered.
**Fix:** check `err.cause?.code` instead. Confirmed the real shape with a throwaway script that forced a genuine duplicate-key insert and printed the full error object rather than guessing.
**Lesson:** don't assume a driver's raw error shape survives an ORM's wrapping layer. When branching on a specific error code, print the actual error object once and look, rather than pattern-matching from memory or from how a different logging path displayed it (vitest's failure output drills into `.cause` automatically when printing, which looks identical to the code being top-level unless you check directly).

### An unordered `.limit(1)` query picked up leftover test data instead of the seeded merchant
**When:** L1-4, first real page load of the dashboard
**What happened:** the dashboard rendered a merchant named `__gate_test_merchant_...` instead of "Northside Coffee Supply Co."
**Why:** `getDemoMerchant()` ran `db.select().from(merchants).limit(1)` with no ORDER BY, so which row came back was whatever Postgres happened to return first — not necessarily the oldest. ### A demo script's own cleanup step got skipped by a transient Neon connection drop

### `audit_log` had no `merchant_id`, and its lookup silently leaked across tenants
**When:** L2-1, implementing real merchant signup, while the app was still single-tenant
**What happened:** while adding merchant auth, noticed `getRecentAuditEntries` matched rows two ways: `moneyActions.merchantId = X` OR `auditLog.moneyActionId IS NULL`. The `isNull` branch existed because some audit rows (denials logged before a `money_actions` row makes sense, e.g. "no spend cap exists") were never linked to a merchant at all — the code comment even said as much and predicted this would need fixing "if multi-merchant support is ever added." With a second real merchant now genuinely about to exist, every one of those merchant-less rows — including the signup/login events I was about to add — would have shown up in *every* merchant's audit trail.
**Why:** the original schema gave `audit_log` a nullable `money_action_id` (correctly, since not every logged decision moves money) but never gave the table its own `merchant_id`, so a merchant-less row had no way to be scoped to anyone. This was invisible with one merchant in the whole system, since "every merchant" and "the one merchant" were the same set.
**Fix:** added a required `audit_log.merchant_id` column, backfilled via the migration (existing rows get their merchant from the linked `money_actions` row, or fall back to the oldest merchant for the handful with neither), and threaded `merchantId` through every `logAuditEntry` call site in `gate.ts`, `dashboard-mutations.ts`, and the signup action. Also added merchant-ownership checks to `setSpendCap`/`revokeAgent`/`reactivateAgent`/`resolveEscalation`, since those had the same latent problem — none of them verified the target agent or escalation actually belonged to the calling merchant.
**Lesson:** a comment saying "this will need fixing if X is ever added" is a marker that X changes correctness, not just scope — treat it as a blocker the moment X actually happens, not as something to revisit later. More generally, single-tenant scaffolding tends to hide its cross-tenant bugs in exactly the branches that exist to handle "no clear owner" cases (nullable foreign keys, merchant-less rows) — those are the first things to re-audit when adding a second tenant.

### A demo script with no `process.exit(0)` looked hung, not finished
**When:** L2-1, verifying the demo-failure scripts still passed after adding merchant scoping
**What happened:** `scripts/demo-failure-cap-exceeded.ts`, `demo-failure-razorpay-rejection.ts`, and `check-dashboard-actions.ts` appeared to hang indefinitely when run through a pipe (`... | tail -60`) — no output at all for minutes, eventually killed as stuck. Running one directly without the pipe showed it had actually printed its full correct output and then just never returned control to the shell.
**Why:** each of these scripts' `main().catch(...)` chain only called `process.exit(1)` in the failure branch; the success path had no `process.exit(0)` and just let the script fall off the end. Node then waits for the event loop to drain, including the module-level postgres.js connection pool in `src/lib/db/index.ts`, which is never explicitly closed — so the process lingers forever on success. Piping through `tail` made this worse: `tail` waits for EOF on its stdin, which never arrives while the upstream process is still "running" (even though it already printed everything), so the whole pipeline looked hung rather than slow.
**Fix:** added the same `.then(() => process.exit(0))` pattern already used correctly in `scripts/seed.ts` and `scripts/integration-proof.ts` to the three scripts that were missing it.
**Lesson:** any one-shot script that holds a DB connection needs an explicit `process.exit(0)` on its success path, not just its failure path — check for this pattern by symmetry whenever adding a new script, since a script that "hangs after clearly finishing" is easy to misdiagnose as a slow query or a real deadlock instead of a missing exit call.

### FK dependency order for cleanup needed a third link once `recovery_attempts` existed
**When:** L3-6, writing `sequencer.test.ts`'s `afterEach` and the two demo-failure scripts' cleanup
**What happened:** the first version of both the test file's cleanup and `demo-failure-recovery-stopped.ts`'s cleanup deleted `payment_failures` before `recovery_attempts`, and separately deleted `money_actions` while `recovery_attempts.money_action_id` still pointed at rows within it — both threw the same class of foreign-key violation already documented in this file for `audit_log`/`money_actions` in Layer 1, just one hop further down a longer dependency chain now that `recovery_attempts` sits downstream of both `payment_failures` and `money_actions`.
**Why:** `recovery_attempts` has two FKs out (`payment_failure_id`, `money_action_id`), so it has to be deleted before *both* of its parents, not just the more obviously related one (`payment_failures`). It's easy to remember the direct relationship a table was created to model and miss the second FK added almost incidentally (`moneyActionId`, to prove an attempt went through the real gate).
**Fix:** delete `recovery_attempts` first in every cleanup path that touches it, before either `payment_failures` or `money_actions`.
**Lesson:** the existing lesson in this file ("cleanup is delete exactly rows scoped to what I made, in FK dependency order") needs a corollary once a table has more than one outbound FK: check *every* FK column on a table being deleted, not just the one that motivated writing the cleanup code in the first place. A table with two parents needs to out-order both.

### The risk layer escalated a recovery attempt for looking like a retried purchase — a real interaction, not a bug
**When:** L3-6, first live run of `demo-failure-recovery-stopped.ts`
**What happened:** attempts 2 and 3 of the same recovery sequence (same amount, same agent, minutes apart) both came back `pending_escalation` from the gate rather than executing — the model-driven risk layer (`risk.ts`, built in Layer 1) flagged "the same amount was requested again recently" and "repeated identical amount within a short timeframe suggests potential automation or fraud."
**Why:** this is correct behavior, not a defect. ### Reward coin redemption's balance check was a plain read-then-compare, not atomic — caught before shipping, not after
**When:** L6-5, writing reward-coins.ts and the gate's reward-ledger settlement branch
**What happened:** the first implementation of `redeemRewardCoins` called `getCoinBalance()` (a `SELECT SUM(coins_delta)`), compared it to the requested amount in application code, and only then wrote the ledger row. Writing the concurrency test for it (the plan explicitly requires one, modeled on `gate.products.test.ts`'s stock test) made the gap obvious before running anything: two concurrent redemptions could both read the same balance, both pass the check, and both insert — over-redeeming a balance that should have blocked the second one.
**Why:** every other atomic resource in this codebase (`spend_caps.spentPaise`, `product_variants.stock`) is a real column, so the existing pattern is a single conditional `UPDATE ... WHERE balance >= amount`. A reward-coin balance is deliberately NOT a mutable column (DECISIONS.md's `recoveredPaise` reasoning: one number derived from the ledger, never two that can diverge) — so the existing conditional-`UPDATE` pattern doesn't apply directly, and a naive port of "check the balance, then write" reintroduced the exact TOCTOU race that pattern exists to prevent.
**Fix:** made the ledger INSERT itself conditional via a raw SQL `INSERT ... SELECT ... WHERE (SELECT SUM(coins_delta) ...) + newDelta >= 0` — the balance is re-derived and re-checked in the same statement as the write, so Postgres serializes it the same way a conditional `UPDATE` does, without needing a second mutable balance column. An issuance (positive delta) always passes; only a redemption (negative delta) is gated by the live sum.
**Lesson:** "the balance must never go negative under concurrency" is the same requirement `spend_caps`/`product_variants` already solved, but the ledger-not-a-column design (chosen for good reasons — see DECISIONS.md) means the standard "conditional UPDATE on a mutable column" recipe doesn't transfer automatically. When a new resource is deliberately modeled as an append-only ledger rather than a mutable balance, its atomicity guarantee has to be re-derived as a conditional INSERT against a live aggregate, not assumed from the existing UPDATE-based pattern. Writing the concurrency test *before* trusting the implementation (rather than after something broke in production) is what caught this here — it never shipped broken.

### Forcing a real Groq auth failure for a demo script: an in-file `process.env` mutation runs too late, and the fix's own fix rediscovered a known pitfall
**When:** L7-6, writing `scripts/demo-failure-explain-degrades.ts`

### A CORS preflight carries no body — putting the embed key in the JSON request instead of a header silently broke every real cross-origin request
**When:** Layer 10 (embeddable widget), L10-3, first attempt at origin enforcement on the buyer endpoints
**What happened:** every unit test passed — `resolveEmbedRequest()`'s pure-logic tests, the route tests, all green. **Lesson:** a route handler test that calls `POST()` directly proves the logic works when a body is present — it says nothing about whether a real browser's preflight, which never sends one, would ever let that `POST` happen at all. ### `onConflictDoNothing({ target: [...] })` needs its partial index's own WHERE predicate repeated, or Postgres rejects the arbiter outright
**When:** Layer 10 (embeddable widget), L10-5, first `enqueueWebhookEvent()` test run against `webhook_deliveries_dedupe_idx`
**What happened:** `enqueueWebhookEvent()`'s idempotency test (two enqueue calls for the same money action should produce one delivery row) crashed on the very first insert with `there is no unique or exclusion constraint matching the ON CONFLICT specification`, not merely failing the dedupe assertion.
**Why:** `webhook_deliveries_dedupe_idx` is a **partial** unique index (`... WHERE money_action_id IS NOT NULL` — `stock.changed` events have no money action and were never meant to dedupe against each other). `onConflictDoNothing({ target: [webhookId, eventType, moneyActionId] })` supplied only the column list. Postgres will not infer a partial index as the `ON CONFLICT` arbiter from a column list alone — the clause's own predicate has to match the index's `WHERE` exactly, or Postgres can't prove the column list uniquely identifies an arbiter and refuses the whole statement rather than guessing.
**Fix:** added `where: isNotNull(schema.webhookDeliveries.moneyActionId)` to the `onConflictDoNothing` call, matching the index's own predicate.
**Lesson:** this codebase already had one working example of the correct pattern (`recovery/intake.ts`'s `recordPaymentFailure()` against `payment_failures_merchant_payment_idx`, also partial) — reading that file first rather than writing the naive column-list version from scratch would have caught this before running anything. See DECISIONS.md's Layer 10 section and the later Layer 11 entry below for the same shape of bug recurring on two more tables — worth grepping `onConflictDoNothing` in this codebase before adding a new partial unique index anywhere, not just after something breaks.

## The CSS reset silently disabled every Tailwind spacing utility, site-wide

**What broke:** The landing page looked, in the user's words, like a garbage website — every section flush against the left viewport edge, no gutters anywhere, cards and text cluttered together with no breathing room. It read as a series of bad layout choices in the new components.

**It was not the components.** `globals.css` opened with an unlayered reset:

```css
*, *::before, *::after { box-sizing: border-box; margin: 0; padding: 0; }
```

Tailwind v4 emits its utilities inside `@layer utilities`, and **unlayered rules always beat layered ones**, regardless of specificity. So that one `*` rule silently overrode every `mx-auto`, `px-*`, `py-*` and `mt-*` in the entire application. Containers stopped centring, section padding collapsed to zero, and vertical rhythm disappeared — everywhere, not just the new sections.

**How it was found:** By injecting a probe element into the live page and reading its computed style rather than trusting the class list:

```js
const t = document.createElement('div');
t.className = 'max-w-[1400px] mx-auto px-6';
// => maxWidth: "1400px"  (works — not layered away)
// => marginLeft: "0px", paddingLeft: "0px"  (never generated an effect)
```

`max-width` surviving while `margin`/`padding` died is the fingerprint: the reset only zeroes those two properties, so only those two lost.

**The fix:** wrap the reset in `@layer base` and drop the `margin`/`padding` declarations — Tailwind's own preflight already zeroes them from inside the base layer, so only `box-sizing` needed to stay. Section padding went from `0px` to `40px` and `mx-auto` began resolving to a real `616px` margin immediately.

**Lesson:** in Tailwind v4, any unlayered global rule is stronger than every utility. A hand-written reset that predates the v4 upgrade will quietly disable whole categories of utility without a single build warning — and the symptom presents as "the new UI has bad layout," which sends you looking in exactly the wrong place. When spacing is wrong *everywhere at once*, suspect the cascade, not the components.

## Routing a reward-coin refund through `attemptMoneyAction` let the live risk layer escalate it — coins never made it back to the buyer

## A model budget's `periodStart` compared the app server's clock against the database's own clock — real spend silently excluded from the sum

**When:** L14-4, `model-router.test.ts`'s "budget already exhausted" test — set a use case's budget to exactly what a real prior Groq call had just cost, then asserted `remainingPaise` was `0`. It came back `1` instead, meaning the real spend that had just happened wasn't being counted at all.
**What happened:** `setModelBudget()` wrote `periodStart: new Date()` — a timestamp from the Node process's own clock — and `getUseCaseSpendPaise()` summed `model_call_costs` rows with `createdAt >= periodStart`, where `createdAt` is stamped by Postgres's own `defaultNow()`. A debug script (a standalone call to `routeCompletion` then `setModelBudget` then a direct read of the `model_call_costs` row) showed the row's real `costPaise` was `1` but `getUseCaseBudgetStatus` still reported `spentPaise: 0` — the row existed, with the right cost, but fell outside the window the spend query was summing.
**Why:** two different clocks were being compared as if they were one. `setModelBudget`'s second call in the test (setting the budget to `first.costPaise`, immediately after the first real call) writes a fresh `periodStart` via the app server's `new Date()`, called at a moment that could be at or after the app's local timestamp for when the Groq call's response was received and its `model_call_costs` row was about to be inserted with Postgres's own, separately-clocked `defaultNow()`. Any timing skew between the two — even sub-second — could put the row's real `createdAt` before the new `periodStart`, and the `gte` filter would silently drop it from the sum. This is not a Groq-flakiness failure (the test's own assertion, not an external 429); it is a real arithmetic bug this feature's own testing caught immediately, before it ever reached the demo script or the dashboard.
**Fix:** two changes to `setModelBudget()` in `model-router.ts`: (1) `periodStart` is now written via `sql\`now()\`` — the database's own clock, matching `model_call_costs.createdAt`'s `defaultNow()`, so both sides of the `gte` comparison share one source of truth; (2) `periodStart` is only set on the row's first creation — `onConflictDoUpdate`'s `set` clause deliberately omits it, so a later budget edit (a merchant raising or lowering their own allocation) never resets the period and silently zeroes out real prior spend. Verified with a standalone debug script re-run after the fix (`spentPaise: 1`, `remainingPaise: 0`, exactly as expected), then the full test file re-run clean (5/5).
**Lesson:** any time a database row's own server-stamped timestamp (`defaultNow()`, `now()`) is compared against an app-generated `new Date()`, treat it as a bug waiting to happen, not just a style choice — the fix is almost always to source both sides from the same clock, which for a comparison against a DB column means letting the DB stamp both sides. This is a different failure mode from the earlier, already-documented postgres-js Date/uuid parameter-binding bug (Layer 13's Guardian) — that one was a driver-level type-binding issue; this one is a genuine two-clocks correctness bug, and worth keeping distinct in memory since the fix for each looks similar (`.toISOString()`/casts there, `sql\`now()\`` here) but the root cause differs.

## Layer 17's `claimDueTasks` left a crashed task's own status stuck at "claimed" forever — its lease expiring did nothing, because status never returned to something reclaimable

**When:** L17-1, writing `tasks.test.ts`'s own "reclaims a task once its lease has expired" test — the very test meant to prove the runtime's central crash-safety claim.
**What happened:** the first implementation of `claimDueTasks`'s eligibility check was `status IN ('pending', 'waiting') AND runAfter <= now() AND (claimedUntil IS NULL OR claimedUntil <= now())`. Writing the two independently (a status enum for "where is this task in its lifecycle" and a separate timestamp for "is the current claim still valid") is a natural design, but it's easy to wire the status half narrowly and forget the lease half is supposed to be able to *reopen* a status the narrow version treats as already-decided. **Lesson:** this is the fifth documented occurrence of the identical FK-ordering gap in this codebase (L18, L19, L21×2, L22, L23, now L24 — see this file's own running count), and the first one caused by a test whose final assertion is *itself* nondeterministic by design rather than by an added feature changing timing. A test that documents its own live-model nondeterminism in a comment ("not simulated") should be read as a signal that its cleanup needs to handle every real outcome branch that call can produce, not just the one the test happens to assert on the happy path.
